## 0. AICompilerの主語・目的・比較対象・設計対象（Owner訂正 2026-11-13）

1. **SUBJECT＝AICompiler。PURPOSE＝現在の技術・機械・規格・知見で、既存機械語への最適なアクセス／アプローチ基盤を確立する。** AIが自然言語から機械操作へ変換する際の最も効率的な記号化・操作・変換を成立させる。
2. **DESIGN_OBJECT＝AIが自然言語の要求・目的・制約から生成・編集・検証でき、既存機械語へ変換できる最適化された操作記号フォーマットと、その決定論的な変換・拒否・検査機構。** 既存言語選定、既存compiler模倣、短い文字列だけの追求、単一CPU用コードの生成だけを目的としない。
3. **RESEARCH_INPUT＝既存言語・compilerの画一化された機械語変換基準／規則と、蓄積された実用上の成果・制約・反例。** 形式仕様・実装ソース・生成物・実行結果・運用条件を同じ対象へ対応づけて照合する。既存採用実績を最適性の証明に置換しない。
4. **CURRENT_MEANS＝AIC/0.2、Rust 2024 compiler、GNU as、Linux x86-64/System V/ELF64 ET_REL、C++20 harness。** 2026-11-09/11採用の限定実装契約は保持する。AIC/0.2の採用は初期変換の施工許可であり、最適な最終記号形式への採用ではない。
5. **NON_GOAL＝機械語・ISA・CPU・メモリ原理そのものの最適化・再設計。** 比較対象としてそれらの現行規格・制約を調査しても、変更する主体・目的へすり替えない。

### 0.1 責任・意味・実物の連鎖

- 自然言語の元要求（目的／条件／制約／文脈）→ AIによる操作記号の生成・編集 → 版付き操作記号 → 意味/関係/適合性検証 → target別の命令選択・配置 → 既存機械語とobject → 宣言済みconsumerによる実行・観測、を一つの追跡可能な系とする。
- AIによる自然言語解釈はcompilerが自動的に保証する能力と混同しない。元要求と記号化結果の対応・残差・誤変換・未表現条件を独立に検査し、意味が不明なら明示的に留保する。compilerは受理した記号の意味を保存する責任を負う。
- 各変換点でsource identity、version、入力意味、制約、出力、拒否、使用toolと版、消失情報、観測証拠を結び、AICompilerによる既存機械語へのアクセス・操作・変換の成立と効率を監査可能にする。
- CPU・OS・ISA・ABI・objectはtarget profileで分離する。現行対応はLinux x86-64だけで、将来の多target構造と実証済み対応targetを混同しない。

### 0.2 既存方式と実績の照合単位

| 観測対象 | 必要な根拠 | 区別すべき境界 |
|---|---|---|
| 言語と意味 | 構文・型・操作・状態・副作用・未定義・入力依存性 | 表現の類似 ≠ 意味の一致 |
| 変換器 | compiler実装と版、optimization flags、内部変換規則・拒否、生成条件 | 実装の慣習 ≠ ISA必須条件 |
| 機械・規格 | ISA、拡張、ABI、OS API、object/link/loader、規範版・条項 | assembler受理 ≠ 規格適合 |
| 現実の成果 | 実生成物・disassembly・機械実行・正答・時間・資源・size・環境 | 普及・実績 ≠ 普遍的最適性 |
| 蓄積された実運用実績 | 公開された運用期間・採用条件・互換性・障害/是正・保守実績とその一次資料・対象版・母集団 | 手元の一回のベンチマーク ≠ 長期運用の実績。普及 ≠ 変換基準の正当性の証明 |
| 比較判断 | 同じ目的/意味/条件の課題群、独立oracle、差分・反例・適用範囲 | 相関・差異 ≠ 原因の証明 |

候補は言語、compiler、IR/bytecode、DSL、schema、形式記述、ISA/ABI等を含む開いた母集団とする。調査資源で深度を保留しても、恒久的な不採用とは扱わない。ただし全候補の調査完了を一気通貫実装の開始条件にしない。**AICompilerの主目的に直結する比較では「同等意味の入力→既存compilerによる変換判断→実生成機械命令→consumerでの現実の結果」の対応を優先し、言語仕様・構文の資料数を実物比較の代用にしない。**

### 0.3 最適化の成立条件

- 「最も効率的」は対象・目的・環境・評価軸・母集団・制約を明示した比較結果を指す。普遍最適を無証拠で宣言しない。
- 比較軸候補：AIの記号生成/修正/再生成の成功率とコスト、意味保存・拒否、診断修復負荷、生成物の実行性能/size/資源、target適合、版進化・再現性。実行性能は既存compilerの実績と出力品質を照合する従属軸であり、機械語そのものを最適化する目的ではない。課題bank、評価指標の重み、下限、統計処理・採用条件は提案とOwner採用を分ける。
- 意味保存・規格適合・安全境界は非緩和条件とし、その範囲内で効率を測る。token最小、byte最小、コンパイル最速、実行最速のどれか一つを全体最適と同一視しない。指標間に対立があればPareto関係と採否理由を保持する。
- AIC/0.2は動作する対照基準として使用。新記号候補は別version・別実験IDで評価する。成果と異なる条件を隠した比較、テスト専用の結果埋込み、実例に特化した仕様緩和は禁止する。

## 1. 目的

人間向け高級プログラミング言語を、AIによるプログラム生成から機械語実行までの**必須中間層**にしない。既存言語・compilerの変換方式と実績を照合し、AIが自然言語から機械操作へアクセスするための操作記号フォーマットを設計・比較最適化する。採用した記号の意味を保存し、指定実行環境に適合する機械命令・生成物へ変換する。

本リポジトリは、過去の機械語再設計、命令運用最適化、メモリ方式再設計の実装内容を自動継承しない独立プロジェクトである。AICompilerの主語・目的を機械語自体の変更へ置換しない。

## 2. システム境界

AICompiler全体の対象連鎖は、**自然言語による元要求→AIによる操作記号の生成/編集→意味・制約検査→既存規格に対する変換→実生成物→consumerの現実の結果→既存方式との同条件比較→操作記号・変換方式の更新**とする。以下はその一部である**現行AIC/0.2限定の実装済み経路**：

`AIC/0.2専用文字列 → 入力解釈・意味検査 → 制約処理・命令生成 → Linux x86-64向け機械命令／ET_REL object`

| 領域 | 責任 |
|---|---|
| AI用入力形式 | 機械的に解釈可能な構文、意味、型／状態／操作の定義 |
| 元要求とAI操作 | 元の自然言語要求・目的・制約の出自と、AI生成記号への対応・未表現・誤解釈の記録。AIの解釈能力をcompiler自身の保証としない |
| 新規コンパイラ | 入力意味の保存、未対応条件の拒否、対象規格への適合 |
| 既存規格 | ISA、ABI、OSインターフェース、実行形式、必要な環境条件 |
| 外部実行環境 | 自らが宣言する規格・条件に従った命令実行・ロード・サービス提供 |
| 検証・証拠 | 対象・版・前提・結果・未実行の識別、根拠を超えない主張 |
| 既存方式の比較 | 同等意味の課題、実compilerの規則・flags・生成命令と実行結果、AI操作効率の根拠を照合し、採否条件と未実証を明示 |

コンパイラ内部にどのような処理段階を置くかは、上の意味・責任境界を保持する限り自由に設計できる。既存IRや既存コンパイラへの依存を事前条件にしない。

## 3. 入力文字列の要求

- 記号形式はAIによる自然言語からの生成・編集・検証を想定し、目的・操作・関係・依存・状態・制約を欠落させない。自然言語全文をcompilerへ直接入力する方式を必須とはしないが、元の要求との対応を検査可能にする。
- 既存変換基準と実績の比較から必要な構成要素を導出する。既存言語への似せ方ではなく、AI操作効率・意味の一意性・機械実行結果で採否を評価する。
- 記号の識別子、局所編集、版進化、構文保持と意味保持は別条件とし、必要な保証範囲を定める。
- AIによる生成・編集・差分・再利用・検証の効率を評価対象とする。
- 人間の可読性、手書きしやすさ、既存言語との類似を必須条件としない。
- 文字列から操作・対象・関係・依存・状態変化・制約を一意に解釈できること。
- 曖昧な入力や非対応操作を正しく拒否できること。
- 文字数やトークン数の短さだけを唯一の最適化指標としない。
- 既存言語・表現の参照母集団は開いておく。プログラミング言語に加え、compiler IR/bytecode、query/constraint/DSL、grammar、data/schema/IDL、形式仕様等も候補地図に含める。調査資源による枝切りは深掘りの順序・深さを保留するもので、恒久的な除外や不採用を意味しない。枝・深度・根拠・再開条件は[参照地図](research/02_既存言語・表現参照地図.md)で追跡する。
- 既存言語・表現を調べる目的は、構文、意味、型、effect、制御/データflow、検査、診断、差分編集、版進化等から設計知識を得ることである。参照結果から構造や機能を自動継承せず、既存言語との類似を設計制約にも優位性の根拠にも置かない。
- Ownerは2026-11-09に、初期実装の入力として**AIC/0.2、1個の`u64`引数を受ける`aic_main(u64) -> u64`のpure function**を採用した。初期操作は`const.u64`、`add.wrap.u64`、`sub.wrap.u64`、`eq.u64`、`phi.u64`、`br`、`br.if`、`ret.u64`。u64演算はmodulo 2^64、`eq.u64`はboolを返し、Phiは実際のCFG predecessor edgeに対応する値を並列代入する。
- 採用範囲の具体的な文法、拒否条件、診断コードは[初期変換契約](proposals/01_初期変換契約案.md)と実装で管理する。AIC/0.2のAI効率優位を示す比較実験は未実施であり、最適性を主張しない。
- B33の現実装容量はsource 1,048,576 byte、256 block、16,384 instruction、Phi incoming総数65,536。公開IRの全識別子は63 byte以内とし、超過は`E_LIMIT`で処理を拒否する。parameterとterminatorはinstruction数に含めない。これは新たな実装制限であり、容量超過sourceをAIC意味上の不正とはしない。β資源保証・総メモリ・時間保証の採用ではない。詳細・適用入口は初期変換契約§2.5、観測は規格調査§3.13。
- B34はassembler objectの観測byte上限を8,388,608（8 MiB）とし、driverは上限＋1 byteまで読み、ELF検査入口で超過を`E_LIMIT`拒否する。一般ELFの妥当性・生成disk量・総heap・実行時間の上限とは区別する。文字列表の終端保証と必須名の固定長比較で反復走査を除去する。観測・未保証は規格調査§3.14。
- B35はGNU asのversion query・assembly invocationごとにstdout/stderr各65,536 byteをcaptureし、direct childのspawn後実行時間を30秒で制限する。capture超過は`E_LIMIT`、期限到達は`E_TOOL`とし、既存outputを保ってinstallしない。これはprocess tree、compiler全体の資源、β資源契約を保証しない。子孫processのkill/waitは行わず、direct child終了後の追加出力も追跡しない。根拠と限定は規格調査§3.15。
- memory、pointer、I/O、syscall、global、複数function、function call、exception、atomic/thread、float/vector、nondeterminism、外部副作用は初期実装の対象外。

## 4. 対象規格・制約の取り込み

対象単位は、少なくとも`CPU/ISA + 拡張 + ABI + OSインターフェース + 実行形式 + 対応版`を明示する。対象外の環境を暗黙に保証しない。

Ownerは2026-11-09に初期targetとして**Linux x86-64 / System V AMD64 ABI / ELF64 ET_REL**を採用した。コンパイラ実装は**Rust 2024 + Cargo**、object生成に**GNU as**を使い、linkerはコンパイラから呼ばず、試験harness側の結合に限る。Ownerの「どちらも採用」という追加指示は、Rustをコンパイラ本体、C++20を独立試験harnessとして採用する意味に適用した。これはRust/C++の二重compiler実装を意味しない。

この選択はR3実装の範囲を定めるが、規格適合の完了を意味しない。Ownerは2026-11-11に最低CPU ISA floorとしてAMD64 psABI 1.0 `baseline`、ELF共通object規則の参照版として安定版`ELF Object File Format 4.2`を採用した。CLI target `x86_64-linux-gnu`はこのCPU profileを指すプロジェクト固有aliasであり、GNU asには`--64 -march=generic64`を渡して生成命令の利用featureを制限する。`generic64` assembler optionは命令集合のguardであり、psABI上のOS feature条件や全規格条項の適合検査を代替しない。AMD64 psABIはmachine-specific ABI/relocationの別参照として残り、ELF 4.3は公式サイト上DRAFTである。Intel SDM Combined Volumes文書ID `671200`、AMD APM Vol. 3 `24594` Rev. 3.37、ELF 4.2の関連条項と現行codegenを照合したが、規格適合は未成立。GNU Binutils 2.44でのassembler acceptance、`readelf`/`objdump` object inspection、harness executionは局所QCであり、全x86-64実機適合の代用にしない。GNU ISA-level property noteの必須化は今回採用せず、別途未決定のままとする。B27では通常関数の引数・結果・stack・保存register・DF・FP制御状態を条項別に監査し、harnessへDF/x87 CW/MXCSR controlのQCを追加した。監査範囲と未実施は[規格調査§3.8](research/01_既存技術・規格調査.md)に記録する。B28はinstall前にsection/string/symbolの限定構造検査と`aic_main`の期待出力shapeを確認する。extended numbering・解釈対象のcompressed table等は非対応であり、一般ELFの不正と区別する。根拠・制限・拒否試験は同記録§3.9を参照。B29では現行producerが出さないREL/RELA、DYNAMIC/DYNSYM、非null未定義symbol、COMMONをinstall前に拒否する。これは一般ELFの不正判定ではなく、採用済みpure functionの現行出力shapeに対する実装制限である。RELR等の後続拡張や機械命令意味はこの検査の保証外で、同記録§3.10へ記録する。

B38はELF 4.2 §2.1と固定AMD64 psABIのheader節を照合し、process entry address（`e_entry`）とprogram header offset/count（`e_phoff`/`e_phnum`）の非zeroを現producerの期待出力外としてinstall前に`E_OUTPUT`拒否する。現compilerはlink用の単一function objectを生成し、process entryやprogram header tableを生成しない。この出力制限を一般ELFの不正判定やprogram headerの完全検査と扱わない。根拠・反例・検査範囲は[規格調査§3.18](research/01_既存技術・規格調査.md)。

B39はELF 4.2 §3のsection header規則に照合し、通常sectionの`sh_addr`が`sh_addralign`に整列しないobjectをELF不正としてinstall前に`E_OUTPUT`拒否する。これはproducer固有のshape制限ではない。整列値0/1の「制約なし」を維持し、section addressの意味全般や全ELF適合は認定しない。根拠・実GNU as反例・検査範囲は[規格調査§3.19](research/01_既存技術・規格調査.md)。

B40はELF 4.2 §3で規定されるsection groupを、現producerが使わない有効なlinker機能として扱う。`SHT_GROUP`および`SHF_GROUP`を持つobjectは、COMDAT selectionによりentry functionがlink時に除去され得るため、install前にunsupported `E_OUTPUT`で拒否する。これはsection groupの一般的な不正判定でも、group機能全体の仕様検査でもない。根拠・実GNU as反例・検査範囲は[規格調査§3.20](research/01_既存技術・規格調査.md)。

B41はELF 4.2 §3.3の`SHT_PREINIT_ARRAY`、`SHT_INIT_ARRAY`、`SHT_FINI_ARRAY`を、現producerが使わない有効なsection typeとして扱う。初期化または終了関数へのpointer arrayを持つobjectは、install前にunsupported `E_OUTPUT`で拒否する。配列payloadや関数pointerの一般検査は行わず、ELF全section typeのallowlistにも拡張しない。根拠・実GNU as反例・検査範囲は[規格調査§3.21](research/01_既存技術・規格調査.md)。

B42はELF 4.2 §3.4の`SHF_TLS`（`0x400`）を、thread-local storageを示す有効なsection flagとして扱う。現行AIC/0.2にはthread-local stateがないため、このflagを持つsectionを含むobjectはinstall前にunsupported `E_OUTPUT`で拒否する。一般TLS modelや他section flagの意味は検査しない。根拠・実GNU as反例・検査範囲は[規格調査§3.22](research/01_既存技術・規格調査.md)。

B43はELF 4.2 §3.4の`SHF_ALLOC`・`SHF_WRITE`・`SHF_EXECINSTR`の意味に照らし、非空の割当sectionを非書込の実行コードに限定する。AIC/0.2にmemory/global stateはなく、現producerの空`.data`/`.bss` sectionは許容する。非空の割当data sectionまたは書込可能な割当sectionは有効なELF機能だが、現producer未対応shapeとしてinstall前にunsupported `E_OUTPUT`で拒否する。非割当section・一般flag検査・機械命令意味検査には拡張しない。根拠・反例・検査範囲は[規格調査§3.23](research/01_既存技術・規格調査.md)。

B44はGNU Binutils 2.44の`as` section attribute `e`（`SHF_EXCLUDE=0x80000000`）を持つobjectを、現producer未対応shapeとしてinstall前にunsupported `E_OUTPUT`で拒否する。section flagがfinal executable/shared libraryからsectionを除外し得るためであり、実GNU asの`.text.aic_main` AXE objectは現行検査を通過し、GNU ld 2.44では参照時に`aic_main` undefinedでlink失敗した。これはGNU Binutils 2.44の文書・source・実観測に基づく限定拒否で、gABI 4.2の不正判定や全linkerの保証ではない。根拠・反例・検査範囲は[規格調査§3.24](research/01_既存技術・規格調査.md)。

B45はELF 4.2 §3.4 Table 3.3の`SHF_MERGE`（`0x10`）を持つsectionを、現producer未対応shapeとしてinstall前にunsupported `E_OUTPUT`で拒否する。GNU as 2.44は実行sectionを`AXM`として生成し、GNU ld 2.44が重複byte要素を統合して`aic_main`のmachine codeを変え、linked executableがSIGSEGVする反例を確認した。これは有効なELF featureのproducer境界であり、一般ELF不正や全linkerの保証ではない。根拠・反例・検査範囲は[規格調査§3.25](research/01_既存技術・規格調査.md)。

B46はELF 4.2 §3.4 Table 3.3の`SHF_LINK_ORDER`（`0x80`）を持つsectionを現producer未対応shapeとしてinstall前にunsupported `E_OUTPUT`拒否する。GNU as 2.44が生成した`AXL`の`aic_main` sectionは通常linkでは期待値42を返す一方、GNU ld 2.44の`--gc-sections`では関連先sectionとともに破棄され、参照symbolが解決できない反例を確認した。これは有効なELF機能と限定GNU ld観測に基づく出力境界で、一般ELF不正や全linker保証ではない。根拠・反例・検査範囲は[規格調査§3.26](research/01_既存技術・規格調査.md)。

B47はGNU Binutils 2.44の`.note.GNU-stack`に`SHF_EXECINSTR`が付いたobjectを、現producer未対応shapeとしてinstall前にunsupported `E_OUTPUT`拒否する。GNU ld 2.44はこのmarkerから`GNU_STACK RWE`を生成し、flagなしの同noteでは`RW`を生成した。現在のproducerはflagなしのnoteを出す。これはGNU固有の出力境界で、ELF一般不正や最終executableのstack permission保証ではない。consumer側の`-z noexecstack`やtarget別defaultはこの検査の対象外。根拠・反例・検査範囲は[規格調査§3.27](research/01_既存技術・規格調査.md)。

B48はGNU `NT_GNU_PROPERTY_TYPE_0`にある`GNU_PROPERTY_X86_ISA_1_NEEDED`を検査し、採用済みAMD64 psABI `baseline`を超える必須ISA levelを持つET_REL objectをinstall前にunsupported `E_OUTPUT`拒否する。baseline propertyとpropertyなしは引き続き許容するため、property noteの必須化は行わない。GNU as/ld 2.44の実object/linkではv4 noteが最終imageの`PT_GNU_PROPERTY`へ伝わった。これはcompilerが生成する単一objectのproperty境界で、後段の全link input・最終image・実CPU適合を保証しない。根拠・反例・検査範囲は[規格調査§3.28](research/01_既存技術・規格調査.md)。

1. 既存言語、表現形式、compiler implementationを広く参照し、必要に応じて構文、意味、validation、診断、差分、変換方式を調べる。LLVM/GCC/CompCertはその一部であり、参照対象全体ではない。
2. 公式のISA・ABI・OS・実行形式仕様と照合する。
3. 規格要求、既存言語/処理系/IR固有の設計選択、未確認事項を分離して記録する。
4. 資源制約で深掘りを保留する枝は、理由・深度・再開条件を記録する。候補の未調査や保留を排除・不採用と読み替えない。
5. 必要な規則を新規コンパイラへ統合し、対象版と出典を追跡可能にする。
6. 既存ソースコードを自動移植せず、第三者ライセンスと独立性を維持する。

## 5. 不変条件と拒否条件

- **意味保存：** 定義済み入力の意味と、生成命令の規定された作用を対応づける。
- **仕様適合：** 出力は宣言した実行条件に対応する規格に適合する。
- **決定性：** 同一の定義済み入力・構成・状態に対して、定義済みの変換結果が再現する。
- **境界保持：** コンパイラの義務と外部実行環境の義務を混同しない。
- **拒否の明確性：** 不明・非対応・矛盾・検査不能を成功へ変換しない。
- **品質の非緩和：** 対応範囲の縮小は可能だが、宣言した範囲の成立条件を弱めない。

## 6. 初期β版の受入条件（案）

本節は**採用済みAIC/0.2の旧R5に関する歴史的なβ受入検討**であり、新たなAICompiler主工程G6（比較選定した操作記号・アクセス基盤のQA/採用）の完了条件に自動転用しない。

Owner採用済みの範囲は上記の単一関数、Linux x86-64/System V/ELF64 ET_REL、Rust/Cargo、GNU asに限る。linkerはtest harness側のみとし、生成物はstandalone executableではない。採用は初期実装の着手・範囲を許可するもので、β版公開や適合宣言の承認ではない。

β受入条件・品質閾値・AI形式の優位性はOwner判断待ちのまま。受入前に必要となる証拠は、採用した入力文字列仕様、対象規格版、変換規則、対応／非対応表、意味保存・規格適合の検査結果、決定性、未実施項目、実行環境条件、生成物の所在である。現在観測済みの局所QCはこの完了条件の一部にすぎない。

シミュレーションや参照実装との比較は、対象範囲の検証に使用できる。ただし実機未実施なら`実機未実施`と記載し、現物動作を保証したと主張しない。全CPU・全OSの検証を初期β版の受入条件に追加しない。
