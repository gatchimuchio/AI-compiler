# AI-compiler 統合仕様書 — 初期正本

- 版：`0.2-initial-implementation`
- 作成：2026-11-02
- 更新：2026-11-09
- 状態：**Owner採用済みの初期範囲でR3一気通貫実装・局所QCを進行中。対象規格の完全照合、R4 QA、β版は未完了・未承認。**
- 主語：AI専用文字列表現を既存機械語に変換する**新規コンパイラ**

## 1. 目的

人間向け高級プログラミング言語を、AIによるプログラム生成から機械語実行までの**必須中間層**にしない。AIが操作する文字列表現を定義し、その意味を保存したまま、指定した実行環境の規格に適合する機械命令・生成物へ変換する。

本リポジトリは、過去の機械語再設計、命令運用最適化、メモリ方式再設計を継承しない独立プロジェクトである。

## 2. システム境界

`AI専用文字列 → 入力解釈・意味検査 → 制約処理・命令生成 → 機械命令／必要な実行形式`

| 領域 | 責任 |
|---|---|
| AI用入力形式 | 機械的に解釈可能な構文、意味、型／状態／操作の定義 |
| 新規コンパイラ | 入力意味の保存、未対応条件の拒否、対象規格への適合 |
| 既存規格 | ISA、ABI、OSインターフェース、実行形式、必要な環境条件 |
| 外部実行環境 | 自らが宣言する規格・条件に従った命令実行・ロード・サービス提供 |
| 検証・証拠 | 対象・版・前提・結果・未実行の識別、根拠を超えない主張 |

コンパイラ内部にどのような処理段階を置くかは、上の意味・責任境界を保持する限り自由に設計できる。既存IRや既存コンパイラへの依存を事前条件にしない。

## 3. 入力文字列の要求

- AIによる生成・編集・差分・再利用・検証の効率を評価対象とする。
- 人間の可読性、手書きしやすさ、既存言語との類似を必須条件としない。
- 文字列から操作・対象・関係・依存・状態変化・制約を一意に解釈できること。
- 曖昧な入力や非対応操作を正しく拒否できること。
- 文字数やトークン数の短さだけを唯一の最適化指標としない。
- Ownerは2026-11-09に、初期実装の入力として**AIC/0.2、1個の`u64`引数を受ける`aic_main(u64) -> u64`のpure function**を採用した。初期操作は`const.u64`、`add.wrap.u64`、`sub.wrap.u64`、`eq.u64`、`phi.u64`、`br`、`br.if`、`ret.u64`。u64演算はmodulo 2^64、`eq.u64`はboolを返し、Phiは実際のCFG predecessor edgeに対応する値を並列代入する。
- 採用範囲の具体的な文法、拒否条件、診断コードは[初期変換契約](proposals/01_初期変換契約案.md)と実装で管理する。AIC/0.2のAI効率優位を示す比較実験は未実施であり、最適性を主張しない。
- memory、pointer、I/O、syscall、global、複数function、function call、exception、atomic/thread、float/vector、nondeterminism、外部副作用は初期実装の対象外。

## 4. 対象規格・制約の取り込み

対象単位は、少なくとも`CPU/ISA + 拡張 + ABI + OSインターフェース + 実行形式 + 対応版`を明示する。対象外の環境を暗黙に保証しない。

Ownerは2026-11-09に初期targetとして**Linux x86-64 / System V AMD64 ABI / ELF64 ET_REL**を採用した。コンパイラ実装は**Rust 2024 + Cargo**、object生成に**GNU as**を使い、linkerはコンパイラから呼ばず、試験harness側の結合に限る。Ownerの「どちらも採用」という追加指示は、Rustをコンパイラ本体、C++20を独立試験harnessとして採用する意味に適用した。これはRust/C++の二重compiler実装を意味しない。

この選択はR3実装の範囲を定めるが、規格適合の完了を意味しない。Intel SDMまたはAMD APMの候補命令条項とSystem V ELF gABIの共通規則は参照資料から未確認であり、R1は進行中。現環境のGNU binutils 2.44でassembler受理・object観測・harness実行を確認した結果を、公式規格照合や全x86-64実機適合の代用にしない。

1. LLVM、GCC、CompCert等の既存コンパイラから命令生成、環境適合、意味保存の実装知識を調査する。
2. 公式のISA・ABI・OS・実行形式仕様と照合する。
3. 規格要求、既存コンパイラの実装選択、未確認事項を分離して記録する。
4. 必要な規則を新規コンパイラへ統合し、対象版と出典を追跡可能にする。
5. 既存ソースコードを自動移植せず、第三者ライセンスと独立性を維持する。

## 5. 不変条件と拒否条件

- **意味保存：** 定義済み入力の意味と、生成命令の規定された作用を対応づける。
- **仕様適合：** 出力は宣言した実行条件に対応する規格に適合する。
- **決定性：** 同一の定義済み入力・構成・状態に対して、定義済みの変換結果が再現する。
- **境界保持：** コンパイラの義務と外部実行環境の義務を混同しない。
- **拒否の明確性：** 不明・非対応・矛盾・検査不能を成功へ変換しない。
- **品質の非緩和：** 対応範囲の縮小は可能だが、宣言した範囲の成立条件を弱めない。

## 6. 初期β版の受入条件（案）

Owner採用済みの範囲は上記の単一関数、Linux x86-64/System V/ELF64 ET_REL、Rust/Cargo、GNU asに限る。linkerはtest harness側のみとし、生成物はstandalone executableではない。採用は初期実装の着手・範囲を許可するもので、β版公開や適合宣言の承認ではない。

β受入条件・品質閾値・AI形式の優位性はOwner判断待ちのまま。受入前に必要となる証拠は、採用した入力文字列仕様、対象規格版、変換規則、対応／非対応表、意味保存・規格適合の検査結果、決定性、未実施項目、実行環境条件、生成物の所在である。現在観測済みの局所QCはこの完了条件の一部にすぎない。

シミュレーションや参照実装との比較は、対象範囲の検証に使用できる。ただし実機未実施なら`実機未実施`と記載し、現物動作を保証したと主張しない。全CPU・全OSの検証を初期β版の受入条件に追加しない。
