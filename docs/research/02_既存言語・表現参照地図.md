# 既存言語・表現の参照地図と調査深度

- 作成日：2026-11-09
- 更新日：2026-11-10
- 状態：**初期の開放型索引。全言語・全版の網羅調査ではない。**
- 目的：既存言語・中間表現・DSL・機械可読形式の広い参照母集団を保ち、資源制約による調査の深さ・順序を追跡する。

## 1. 基本方針

本プロジェクトでは、新しいAI操作用言語を設計するために、既存の言語・表現を広く参照する。文字通りの全言語・全方言・全版・全処理系を一度に深読することは現実的でないため、**参照対象を先に狭く固定せず、まず枝を地図に残し、資源制約は各枝の調査深度と着手順へ反映する。**

「参照」は、構文や文法だけでなく、意味、型、制御・データフロー、状態・副作用、検査、診断、差分更新、拡張・版管理、既存の変換や実行モデルから設計知識を得ることを指す。参照対象への登録、資料確認、実装の分析はいずれも、その形式の採用や実装を意味しない。特に、現行AIC/0.2の採用は初期実装範囲を定める決定であり、他形式の調査を不要にする結論でも、AIC/0.2の優位性が比較実証された結果でもない。

同じ名称の下に異なる種類の対象を混同しない。少なくとも、(a)言語仕様、(b)具体的処理系、(c)コンパイラ内部IR、(d)VM/bytecode/機械語、(e)シリアライズ形式、(f)スキーマ/IDL、(g)文法・メタ言語、(h)規格・形式記述を区別して記録する。分類は交差を許し、以下の例は入口を作るための種であって、完全な一覧でも、各項目を調査済みとする宣言でもない。

## 3. 調査深度と採否を分ける記録方式

調査深度は候補ごとに次の段階で記録する。特定版・資料・対象に結び付けられない一般知識だけで深度を上げない。

| 深度 | 到達条件 |
|---|---|
| M0 地図登録 | 枝と候補名を記録した。資料の確認や性質の主張はしていない |
| M1 概観 | 公式project/spec/sourceの入口、対象版、対象種別、見るべき論点を識別した |
| M2 一次資料照合 | 具体的な問いに対して公式仕様/文書の該当箇所を読み、版と所見を記録した |
| M3 深掘り | 実装・test suite・複数版/方言の差を確認したか、必要なprototype/比較実験を実施した |

**採否状態は別欄**で、`未判断`、`初期実装に採用`、`比較候補`等を記録する。`M0/M1`、今回深掘り保留、または調査未完了は、排除・無関係・不採用の意味を持たない。資料にアクセスできなかった時も枝を消さず、未確認と制約を記録する。

## 4. 資源配分と今バッチの深掘り保留

調査順序は、今後の設計判断に与える影響、意味誤りの危険、複数枝への再利用性、候補間の差を識別できる見込み、一次資料の入手性、読解・実験コストを見て決める。言語の知名度だけで優先度を決めず、トークン数の少なさだけで入力形式を評価しない。

まず枝と代表候補を広く登録し、次に共通論点を横断して概観し、設計判断に効く枝の一次資料へ深く進む。全候補のprototypeを作るのではなく、比較結果で決定が変わり得る候補に絞って実験する。枝を深掘り保留にする場合は「保留する調査範囲」「今その深さまで進まない資源上の理由」「再開条件」「現在の深度」を記録する。設計に直結する反例、意味差、未解決の規格要求が見つかった時は、予定順を繰り上げる。

**現在のR1で先に横断する問い：** (1) text/structured/binary表現と局所差分の保持、(2) parser受理・型/整形式検査・意味定義の境界、(3) function/control-flow/effect/stateの表現、(4) version/schema進化と診断、(5) IR lowering・codegen・形式証明の接続、(6) memory reference/object identity・lifetime・aliasing・access bounds。優先深度は設計判断に影響する候補から進めるが、未着手のlanguage familyやlogic/constraint、array/science、GPU/hardware、formal、historical等を候補地図から外さない。優先順は、各枝で判断に影響する知見が現れた時に更新する。

| 今回の調査枝切り | 現在の扱い・理由 | 再開条件 | 排除・不採用を意味するか |
|---|---|---|---|
| 全言語・全方言・全版を一件ずつ通読 | まず代表枝・共通論点の索引化を行い、全個別項目の全版通読は保留。組合せが大きく、版更新も続く | 候補形式・意味要件が絞れた時、または版差が判断に影響する時 | いいえ。対象枝は索引に保持し、必要な時に再開する |
| 歴史的・esoteric・希少な各言語を個別に実装分析 | 分野名と代表候補を登録し、各処理系・各dialectの深掘りは保留 | 新しい意味モデル、極小記法、構文設計上の反例を探す時 | いいえ。今回の優先深度を下げているだけ |
| 全ドメインDSLを同じ深さで比較 | 代表群を地図化し、個々のpolicy/DB/graphics/HPC等は機能要求が現れるまで深掘り保留 | 対応operation、データ型、副作用、runtimeを追加する設計時 | いいえ。機能別の再開条件を保持する |
| すべての構文候補・シリアライズ形式のベンチマーク | AIC/0.2採用済み範囲を維持し、全候補のAI生成比較・編集実験は保留。測定設計と母集団を先に定める必要がある | QA目標・課題セット・評価指標をOwnerが定め、候補差が設計判断に使える時 | いいえ。AIC/0.2の優位性を主張せず、他形式も比較候補として残す |
| 既存compiler/IRの全ソース・全pass・全targetを網羅解析 | LLVM/GCC/CompCertについて既存記録の範囲に限って比較済み。その他および各実装全域は調査コストに応じて保留 | 問題になったpass、IR、target、proof境界を特定した時 | いいえ。限定調査の結果を全体評価へ拡張しない |

これらは調査深度を制御する本バッチの記録である。将来の設計判断で再評価でき、参照対象そのものを恒久的に狭める規則ではない。

## 5. 比較時の共通質問

候補ごとに該当する問いだけを使い、言語間で意味の異なる用語を同一視しない。

- 構文とgrammar：曖昧性、token境界、括弧/改行規則、位置情報、error recovery、incremental parseはどう扱うか。
- 意味と制約：型、値域、overflow、未定義/未指定/poison、評価順、停止、例外、effect、副作用、nondeterminismをどう定めるか。
- 制御・データ：CFG/SSA/Phi、loop、pattern matching、closure、continuation、並列処理、alias/stateをどう表すか。
- AIによる操作：新規生成、局所変更、差分、再利用、検証、修復で、形式上どの情報が安定しているか。未確認の利点を推測で事実にしない。
- 診断・進化：不正入力の診断、source mapping、schema/version evolution、unknown construct、互換性の方針はどうなるか。
- compiler境界：形式検査、IR lowering、codegen、runtime/ABI依存、証明やtestの対象範囲をどう分けるか。
- 導入条件：一次資料の状態、処理系差、license、toolchain/runtime、保守負担をどう確認するか。

## 6. 代表資料の入口

以下はM1以降の調査で版・対象箇所を固定するための入口であり、この一覧だけで内容を深く確認したとはみなさない。時点で変わる文書は、調査時に版とアクセス日を記録する。

- [The Rust Reference](https://doc.rust-lang.org/reference/) — Rust言語の主参照文書。最新版は更新されるため、調査時にedition/releaseを固定する。
- [Python Language Reference](https://docs.python.org/3/reference/) — Pythonの構文とcore semanticsの参照入口。実装詳細や標準libraryの記述とは区別する。
- [ECMAScript Language Specification](https://tc39.es/ecma262/) — ECMAScript仕様の現行入口。JavaScriptという実装・環境全体と仕様本文を区別する。
- [Haskell 2010 Language Report](https://www.haskell.org/onlinereport/haskell2010/) — 現行の版付きbaseline入口。2026-08-04に改訂report作成の活動が告知されているため、深掘り時は[改訂report活動](https://blog.haskell.org/revised-haskell-2010-report/)の進捗も確認する。後年のextensionや処理系の挙動は別に確認する。
- [SWI-Prolog Reference Manual](https://www.swi-prolog.org/pldoc/doc_for?object=manual) — Prolog処理系資料の入口。Prolog一般の標準とSWI固有機能を分離して読む。
- [ISO/IEC 9075-1:2016, IEC listing](https://webstore.iec.ch/en/publication/59678) — SQL標準の公式販売・概要ページ。個別版・partの規定はアクセス可能な一次資料で確認する。
- [SPARQL 1.2 Query Language](https://www.w3.org/TR/sparql12-query/) — W3Cの問合せ言語文書。状態がWorking Draft等であれば安定規格と混同しない。
- [Protocol Buffers language specification](https://protobuf.dev/reference/protobuf/edition-2024-spec/) — `.proto`定義言語の版付き仕様入口。serialization wire formatと定義言語を区別する。
- [RFC 8259 JSON](https://www.rfc-editor.org/rfc/rfc8259)、[JSON Schema specification](https://json-schema.org/specification)、[YAML 1.2.2](https://yaml.org/spec/1.2.2/)、[Protocol Buffers editions guide](https://protobuf.dev/programming-guides/editions/) — data model、schema dialect、mapping order、field-number evolutionの一次資料。
- [LLVM Language Reference](https://llvm.org/docs/LangRef.html) / [MLIR Language Reference](https://mlir.llvm.org/docs/LangRef/) — compiler IRの参照入口。IRをsource-language inputと混同しない。
- [WebAssembly Core Specification](https://webassembly.github.io/spec/core/) — VM instruction semantics、validation、text/binary形式の入口。embedding/API層とは分ける。
- Compiler実装の固定版資料・観測は[既存技術・規格調査](01_既存技術・規格調査.md)を参照する。

## 7. この更新で確認した資料入口（M1。深い比較ではない）

2026-11-09に公式・一次資料の入口と文書自身が示す適用範囲を確認した。以下は調査の足場であり、例示言語全体の比較、各処理系の検査、設計採否を終えたという意味ではない。

特定の構文/検証/形式分離問いについて一次資料を読んだM2結果は[初回横断比較](03_入力表現・構文・検証境界比較.md)に記録した。各family全体の深度は引き続きM0である場合がある。

構造化データの局所編集、順序/識別、未知要素、schema evolutionのM2照合は[構造化編集・版進化の限定比較](04_構造化編集・版進化比較.md)に記録した。JSON・YAML・Protobuf等のfamily全体、全processor、AI編集性能は未調査であり、未着手の枝を参照母集団から除外しない。

制御フロー、評価順、副作用/状態、例外・探索のM2照合は[制御フロー・効果・状態モデル比較](05_制御フロー・効果・状態モデル比較.md)に記録した。そこでの深度はC11 draft、Rust current reference、Haskell 2010、ECMAScript 2025、SWI-Prolog manual、current LLVM、WebAssembly 3.0の特定問いに限り、各language familyの全実装・全版には拡張しない。

整数型幅、値域、overflow、bitvector interpretationのM2照合は[整数型・数値境界の限定比較](06_整数型・数値境界意味比較.md)に記録した。Python 3.15.2、Haskell 2010、ECMAScript 2025、C11、C++ WG21 N4861 public working draft、Ada Reference Manual 2022 Edition、Fortran 2018 J3 WD 1539-1、ECMA-334 7th Edition C#、Swift Book `swift-6.4-fcs` documentation snapshot、Zig Language Reference 0.17.1、Rust、Go 1.27、Java SE 25 JLS、LLVM IR、WebAssemblyの記載深度は当該numeric questionだけである。Swiftについては公式ガイドの該当記述だけでformal standardとは扱わず、Swift compiler observationはNOT_RUN。Zigについてはversioned official documentationの該当記述だけを記録し、local compiler/runtime observationはNOT_RUN。別release/runtime/未調査の整数言語やfloating/decimal/rational/vector系も含め、N4861の最終ISO C++20との差/他edition/compiler、Ada/Fortran/C#の他edition/compiler、Zigの他release/target、Javaの他JLS edition/JDK/compiler等を参照母集団から除外しない。

メモリ参照値、object/allocation lifetime、alias/access条件、bounds違反のM2照合は[メモリ参照・寿命・アクセス境界の限定比較](07_メモリ参照・寿命・アクセス境界比較.md)に記録した。C11 N1570、current Rust Referenceとcore::ptr 1.99.1、Java SE 25、Python 3.15.2、WebAssembly Core 3.0 linear memory、current LLVM IRの該当問いだけを扱う。C++20、他言語・版・処理系・IR、Wasm GC/host memory等の枝は各familyへ一般化せず、理由・深度・再開条件付きで残す。

diagnostic obligation、位置情報、structured output、recovery boundaryのM2照合は[診断義務・診断データ・エラー回復の限定比較](08_診断・位置情報・エラー回復比較.md)に記録した。C11 N1570、WG21 N4861 public working draftの`[intro.compliance]`だけ、GCC 14.2.0 diagnostic-format manualとDebian g++ 14.2.0の単一local observation、Java SE 25 JLS Chapter 1/`javax.tools` Diagnostic APIとOpenJDK 21.0.13の一入力観測、Python 3.15.2 `SyntaxError` API、Node.js v24.22.1 CLI/VM APIと一入力syntax-error観測、current rustc JSON Output manualとpinned rustc 1.99.1の一入力観測、JSON Schema Core 2020-12の特定claimを扱う。N4861の所見は最終ISO C++20規格・他editionへ、GCCの所見は他version・frontend・C++規格へ、Javaの所見は他JLS edition・JDK/compiler実装へ、Nodeの所見はECMAScript edition・他JS engine/Node releaseへ、rustcの所見は他release・flag・診断classへ一般化しない。各言語・compiler・runtime・validator familyや未着手枝の全体へ一般化せず、候補母集団は開いたままにする。

## 8. 調査レコードの最小項目

枝を実査・保留する時は[既存技術・規格調査](01_既存技術・規格調査.md)または専用の調査記録に、最低限次を残す。

```text
対象名 / 対象種別 / 所属する参照枝
版・方言・実装 / 一次資料URL・固定commit・調査日・該当箇所
調査深度(M0-M3) / 採否状態(独立)
調べた設計問い / 観測事実 / 推論 / 未確認
このプロジェクトへの示唆 / 適用限界 / license・tool依存
今回保留する深さ・資源理由 / 再開条件
```

候補一覧を増やしただけで調査済みと表現しない。個別言語を調べた場合も、その言語・版・処理系の範囲を示し、同じfamily全体へ主張を一般化しない。
