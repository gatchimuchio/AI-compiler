### 2.1 規格と実装の区別

ISA命令の意味・encoding、ABIの関数境界・register役割、OS call boundary、object formatのheader/section/relocationは別の規範領域である。LLVMのlegalization、GCCのRTL、CompCertのCoq変換列は各実装の選択であり、同一のIR・最適化器・register allocatorを新規compilerに要求しない。B2案ではソース意味を先に固定し、targetごとの命令選択とABI適合を別段階に置く。

### 2.2 GCCのregister allocation・ABI・出力境界

GCC公式online manualはプロキシ制限で読めていない。GCCの16.2.0 source mirror内の該当manual sourceとpass descriptionから、Machine Descriptionsに加えて以下を確認した。

- gcc/doc/tm.texi.inのRegister Usage/Register Classesは、固定register、call-used/call-saved、allocatable register、instruction operandが使えるregister classをtarget側で記述する。Stack Layout and Calling Conventionsにはregister/stack argument、scalar/aggregate return、caller-save、function entryのtarget hooksがある。これはGCC backendの仕様であり、System V ABI等の規格そのものではない。
- gcc/doc/passes.texiのRegister allocationは、pseudo-registerをhard registerまたはstackへ割り当てるIRAとreload/LRAを説明する。live range、register pressure、spill等が実装責任となる。Final passはmachine descriptionから生成した出力を使ってassembler codeを出す。
- GCC driverはassembler/linker等の外部programを呼び、通常のcompile pipelineでassemblyからobjectへ進み、必要ならlinkする。instruction matching、register allocation、ABI定義、assembly出力、object/link orchestrationを分けて調べる必要がある。

### 2.3 CompCertの証明段階と外部tool境界

CompCert 3.18の公式commented Coq development一覧では、RTLからLTLへのregister allocationに「validation a posteriori」が付き、Allocation/Allocproofが対応する。LTLからLinearへのCFG linearization、LinearからMachへのactivation record layout、MachからAsmへのassembly emissionにも個別のproof moduleがある。Compiler moduleは段階を合成したwhole-compiler semantic preservation theoremを示す。この境界は証明をcompiler全体へ繋ぐ例だが、証明はCompCert Cと形式化済みtarget modelの範囲に限られる。

ccomp driverはMachからAsmを出し、-Sはassembly、-cはobject-only、通常link時にはAssembler/Linker driverを通じてtoolchainを呼ぶ。意味保存証明と、実際のassembler・linker・runtimeを含む配布系は別の境界である。CompCert licenseはNon-Commercialを基本とするため、証明moduleやbackendを本プロジェクトへ転用しない。

## 3. ターゲット規格候補の実査

### 3.1 x86-64 System V ABI / Linux / ELF

- System V Application Binary Interface, AMD64 Architecture Processor Supplementは文書版1.0。参照したx86-64 psABI sourceはcommit e1ce098331da5dbd66e1ffc74162380bcc213236。候補はLP64とし、ILP32/x32を除外する。
- ABIの引数例は整数引数をRDI、RSI、RDX、RCX、R8、R9へ割り当てる。process entryのstackは16-byte aligned。AMD64 ELF、symbol、relocation規則も同資料に含まれる。
- Linux kernel entry_64.S、commit 7475ea8b58616b33c04afb976cf0fbaad9dd63fbでは、64-bit SYSCALLのRAXが番号、RDI/RSI/RDXがarg0–2、R10がarg3、R8/R9がarg4–5。SYSCALLはRCXを戻り先に用いるため、Linux syscall ABIを通常関数ABIと混同してはならない。
- **ISA参照：** 現行codegen命令の一次資料照合は§3.5に記録した。最低CPU ISA feature baselineは未選定で、具体条件に対する最終照合が残る。

### 3.2 AArch64 / Linux / ELF

- Arm ABI official release 2026Q3、commit a1b53459479e88f3492ca9b11a161313764ab138。AAPCS64は2026-11-03発行と記載。同一releaseのAAELF64も確認した。
- AAPCS64はX0–X7をparameter/result registers、X19–X29とSPをcallee-savedとする。SPはメモリアクセス時とpublic interfaceで16-byte aligned。AAELF64はELFCLASS64、EM_AARCH64 (183)、byte order、relocationを定義する。
- B2候補は生成関数にsystem callを許さない。従って初期入力意味の外側にLinux syscall ABIを置く。追加時はLinux arm64 platform ABIとArm ISA/exception semanticsを調べる。
- **未確認：** Arm Architecture Reference Manual for A-profile (DDI 0487)の命令・feature・例外仕様。AAPCS64/AAELF64だけではA64命令を検証できない。

### 3.3 Windows x64 / Microsoft ABI / COFF・PE

- **ABI資料：** Microsoft x64 Calling Convention。MicrosoftDocs/cpp-docsのcommit f29e25fb8f05bb38cf0246476b5c1fc92bf33876にあるページを2026-11-09に取得した（front matter ms.date 2025-03-19、SHA-256 **043986cc9256b62c29b4b18fba978cfece03da69e8680054d210d40b625d89c0**）。参照位置は「Calling convention defaults」「Alignment」「Unwindability」「Parameter passing」「Return values」。64-bit scalar整数引数は位置順にRCX、RDX、R8、R9、integer resultはRAX。callerはcallee向け4 register parameter分の32-byte shadow storeを用意する。stack alignmentとunwindable prolog/epilogに規則がある。
- **形式資料：** Microsoft PE Format、MicrosoftDocs/win32 commit 51101843c83ca4a1ce7db51b0723290a4aa1203cを2026-11-09に取得した（front matter ms.date 2026-09-10、SHA-256 **538d80c5cfa7a72224e1bdaf9d14a63bbec9160c26b1d23017c134a4662b70d1**）。参照位置は「COFF File Header」「Machine Types」「Optional Header」「Section Table」「COFF Relocations」「COFF Symbol Table」。COFF objectとPE imageを区別し、AMD64 machine value 0x8664、PE32+ optional header magic 0x20b、section/symbol/relocationの役割を記載する。object fileではoptional header sizeが0で、最終PE imageはlinkerが作る。Microsoft page自身が仕様の完全性を保証しないと注意している。
- **OS境界：** B2の初期契約候補ではOS APIとsyscallを除外し、Windows ABIに従う関数objectだけを生成する。実行可能PE image、Windows runtime/loader、Win32 API接続は別のlink/run契約である。
- **適用限界：** 本資料はWindows ABI・PE形式を補うもので、x86-64 ISA根拠は§3.5に別記した。Windows target自体は未採用で、Windows toolchain・実行環境でのQAは未実施。

### 3.4 ELF Object File FormatとgABI共通object規則

公式サイトは安定文書を`/v42/elf/`に、現在の`/elf/`を **ELF Object File Format 4.3 DRAFT** と表示している。公式Forewordによると、独立したELF Object File Format仕様はSVR4 gABIのChapter 4–5のobject-file記述を置き換える。したがって参照選択は「gABI全体の版」ではなく、gABI共通object規則を定めるELF Object File Format文書の版として記す。安定版4.2のChapter 2 (ELF Header)、Chapter 3 (Sections)、Chapter 5 (Symbol Table)、Chapter 6 (Relocation)を参照し、4.3は草案として識別した。ELF headerは`e_type`、`e_machine`、version、table offsets/entry sizesを持つ。`ET_REL`、section-header relationships、symbol binding/type、relocation recordとarchitecture-specific relocationをpsABIで定義する境界を確認した。

既存testの生成objectについて、`readelf`は`ELF64`, `REL (Relocatable file)`, `Advanced Micro Devices X86-64`、global `aic_main` symbol、relocationなしを確認し、`objdump`は`aic_main` disassemblyを確認する。driverのheader checkはELF magic、ELFCLASS64、little-endian、`ET_REL`、`EM_X86_64`、ELF version 1、64-byte ELF headerを検査する。機械番号62 (`EM_X86_64`)とrelocation typeはELF共通object形式ではなくAMD64 psABI側の定義である。これらの限定照合はELF全章の適合やlinker/runtimeの成立を示さない。ELF Object File Format 4.2を契約参照版へ採用するOwner決定も未記録である。

### 3.5 Intel 64 / AMD64 ISAと生成命令

Intel公式manual listingのCombined Volumes文書ID `671200`（listing date 2026-09-24）を参照した。Intelのmanual一覧はinstruction referenceがVolume 2にあり、最新版listingの更新日は2026-10-09である。AMDの`24594_3.37`は*AMD64 Architecture Programmer’s Manual Volume 3: General-Purpose and System Instructions*, Revision 3.37, 2025-07-02である。両資料の命令表・long-mode形式と`src/x86_64.rs`の出力を照合した。

現行codegenが出力する実命令は`pushq`, `movq`, `movabsq`, `subq`, `addq`, `cmpq`, `sete`, `movzbq`, `jmp`, `jne`, `leave`, `ret`である。GNU assembler記法の`suffix`や`movabsq`はISA命令encodingそのものの識別名ではなく、対応する`MOV`/`ADD`/`SUB`等のoperand size・operand formを選ぶ表記である。Phi edge-copyはstack slotsへのload/storeとして`MOV`で実装され、optional vector/bit-manipulation extension命令は使われない。

64-bit `ADD`/`SUB`はdestination widthの結果を書き、flagsにcarry/overflow等を反映する。compilerは64-bit結果だけを使いflagsを保持しないため、AIC wrap意味のmodulo 2^64と対応する。`CMP`は値を保存したまま差をもとにstatus flagsを設定し、`SETE`は`ZF=1`をbyteの1として書き、`MOVZX` form (`movzbq`) がbool値を64-bitへzero-extendする。`CMP`後の`JNE`は`ZF=0`条件を用いる。`PUSH`/`LEAVE`/`RET`はstack frameとnear returnの形を構成する。これらの命令意味確認はAIC操作の意味保存全体、全例外状態、object linkや実機動作の完全証明ではない。

Owner採用済みtarget名はLinux x86-64だが、最低CPU世代・named microarchitecture・正式なISA feature baselineは選ばれていない。現行命令表からoptional extensionの要求は見つからなかったが、これを全Intel/AMD x86-64 CPU対応や特定`x86-64-vN`保証へ昇格させない。Linux x86-64の具体的最低feature floorを契約化し、その条件で生成operand/encodingを再照合する作業が残る。

### 3.6 最低CPU feature baselineの候補（未採用）

AMD64 psABI 1.0の固定source（commit `e1ce098331da5dbd66e1ffc74162380bcc213236`）は、AMD64 baseline featureとして`CMOV`, `CX8`, `FPU`, `FXSR`, `MMX`, `OSFXSR`, `SCE`, `SSE`, `SSE2`を列挙し、追加の名前付きmicro-architecture levelは`x86-64-v2`から始まるとする。従ってv2以上を選ぶとbaseline以外のfeatureを最低要件へ追加する。

本sessionで`examples/branch_phi.aic`を現行compilerとGNU Binutils 2.44でobject化し、`objdump -dr`が出す命令を確認した。`PUSH`, `MOV`, `ADD`, `SUB`, `CMP`, `SETE`, `MOVZX`, `JMP`, `JNE`, `LEAVE`, `RET`の範囲で、v2以降の拡張命令は観測されなかった。`readelf -n`にISA levelを示すGNU property noteもなかった。driverのtarget選択は`x86_64-linux-gnu`というtripleのみでfeature profileを指定しない。これは当該fixtureと現行codegenの観測であり、将来の全入力・全生成形・実機CPUを保証しない。

**推奨候補（Owner未採用）：** 初期targetの最低条件をAMD64 psABIの`baseline`に置き、v2以上を要求しない。既存のLinux x86-64 targetと一致する公開済みの最低profileを使える一方、現行scalar-GPR codegenが直接必要とする以上のfeature（例：SSE/SSE2等）も契約floorに含む。実際の出力命令だけを要件とする独自subsetはCPU floorを狭め得るが、標準levelではなく、operand/encoding、ABI、OS実行条件まで独自に管理する必要がある。採用時には`x86_64-linux-gnu`がbaselineを意味することを正本に明記し、将来optional featureを追加する場合の拒否条件を定める。オブジェクト自身にもfloorを記録するなら、GNU linkerが提供する`.note.gnu.property`のISA-level metadata対応を別途仕様化・検査する必要がある。

### 3.7 ELF common object specification版の候補

**推奨候補（Owner未採用）：** ELF common object規則の契約参照版に、2025年公開の安定版`ELF Object File Format 4.2`を使う。`ELF Object File Format 4.3`は公式ページ上DRAFTであり、新たな規則には`SHT_NOBITS`の`sh_offset`、relative relocation、symbol visibility、圧縮ET_REL section等が含まれる。現行objectはdynamic/relative relocation、圧縮section、新しいvisibility flagを使わない一方、空の`.bss` `SHT_NOBITS` sectionは出力するため、4.3を候補とする場合は同sectionの規則を個別再照合する。AMD64 psABI v1.0のmachine-specific ABI/relocation規則はELF共通仕様と別に固定する。

## 5. R1を完了するための残り

一次資料本文の照合と推奨比較を実施した。R1の残りは、(1) AMD64 psABI baseline等のminimum CPU/ISA feature floor、(2) gABI共通object規則に用いるELF Object File Format 4.2または公開中の4.3 DRAFTの参照版、をOwnerが採用すること。採用後、その具体条件で命令formsとELF clausesを再照合する。現段階ではIntel/AMD vendor-wide互換や選択版への適合を宣言しない。
