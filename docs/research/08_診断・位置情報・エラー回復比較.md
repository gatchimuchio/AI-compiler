## 1. 問いと適用範囲

不正な入力を見つけた時、一次仕様が診断の生成を要求するのか、言語・API・validatorがどの位置情報や機械可読構造を定義するのか、診断後に処理をどう回復するかを切り分ける。比較するのは診断義務・診断データの一部であり、文法全体、parser algorithm、全エラー文、IDE機能の調査ではない。

「入力が不正と定義されること」「診断の提示」「複数errorからの回復」「object/codeを生成すること」は別の性質である。特定のcompilerやvalidatorにある便利な出力形式を、その入力言語全体の保証に読み替えない。

## 4. 比較から得た分離規則と未決事項

この資料群は、少なくとも四つの別設計対象を示す。

1. **義務・検出時点：** C11 N1570はsyntax/constraint違反、C++ N4861 draftはより広いdiagnosable syntax/semantic rules（明示された例外を除く）を対象に、それぞれのminimum diagnostic obligationを記す。N4861のdraft claimは最終C++20規格との差を確認していない。JLSのcompile-time/runtime error区分も、利用者向けmessage schemaの代わりではない。
2. **診断データ：** Python `SyntaxError`、rustc JSON、Java `javax.tools.Diagnostic`は異なる境界のinterfaceで、line/column/byte offsetの単位も同一ではない。Java APIはsource objectとcharacter offset rangeを公開するが、code/messageをimplementation-dependentとする。
3. **validator output：** JSON Schemaの位置はinstance/schema内のJSON Pointerであり、source-text spanやcompiler recovery statusを表すものではない。
4. **compiler-specific formatとAIC現行動作：** GCC 14.2.0 manualはJSON/SARIF formatting interfaceを文書化し、ローカルのg++ buildは一つの不正translation unitから3件を出した。Rust JSON manualとlocal rustc 1.99.1 runでは、3件のspan付きerrorに加えてtermination recordsを観測した。AIC/0.2は別の不正入力で最初に該当した`E_UNSUPPORTED_OP`一件を返し、CLI exit code 2でobjectを作らなかった。対象言語・違反・処理系が異なるため、これは出力境界の例であって品質・回復能力の比較試験ではない。GCC/Rustのformatをlanguage規格要件やAICへの採用と解釈しない。

AICについては、今後必要になった時に次を独立して決める。ここでは何も採用しない。

- 1入力で返すdiagnostic数、複数候補からprimary errorを選ぶ規則、phase横断の優先順位。
- codeのversioningと互換性、detail文言の安定度、外部tool stderrの露出・正規化。
- positionの単位、end-span、multi-line range、global errorとsource-associated errorの区分。
- strict compiler pathと、将来のeditor/incremental validation用recovery pathを同じ契約にするか。
- recovery後にどの状態まで検査・生成を続けてよいか、および部分結果を成功と誤認させない方法。
