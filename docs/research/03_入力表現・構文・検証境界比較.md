# 入力表現・構文・検証境界の初回横断比較

- 調査日：2026-11-09〜2026-11-11
- 状態：**特定の設計問いに対する一次資料の限定比較。2026-11-11にTree-sitter v0.27.2の増分parse/edit APIを追補。言語全体の評価・網羅調査・採否決定ではない。**
- 参照母集団と深度方針：[既存言語・表現参照地図](02_既存言語・表現参照地図.md)

## 1. 問いと範囲

同じテキストが「tokenize/parseできる」「型や構造の検査を通る」「定義された意味を持つ」のどこまでを保証するか、また文法・処理系・内部/保存表現をどう分けているかを調べた。これはAI入力文字列に必要な構文、検証器、診断、将来の差分処理を設計するための比較である。

代表例として、命令型・関数型・動的言語からRust、Python、Haskell、ECMAScriptを、compiler IR・VM・schema表現からLLVM IR、MLIR、WebAssembly、Protocol Buffersを調べた。SPARQLは仕様の成熟度を確認する対照に含めた。選択した文書の状態は異なり、固定版の標準、現行更新文書、Working Draft、処理系に強く結び付く資料を同じ確度の「言語規格」とみなさない。

初期入力のAIC/0.2はOwner採用済み契約と実装を基準例として参照する。比較対象の機能をそのまま採用したり、読みやすさ・編集効率・AI生成精度の優劣をこの資料調査だけから結論したりしない。

## 3. 比較結果

### 3.1 文法の形式と字句境界は一つの型に揃わない

- Rust Referenceのgrammar summaryはlexer grammarとsyntax grammarを分け、identifierの先頭・継続文字にUnicode XID規則を使う。さらにraw identifiers、lifetime、複数種の文字列/byte/C-string literal等を記述する。これはRustという広い言語のtoken設計を示すもので、AI専用形式へUnicodeやliteral種類を持ち込む推奨ではない。
- Python 3.15.2のfull grammarはPEG表記を使い、alternative cut `~`、lookahead、eager parse等を定義する。`invalid_` grammar rulesは通常の初回parseではなく、syntax errorを具体化する第二passで使われる。公開grammarはCPython parserを生成するgrammarから導出されると明記される一方、code generationとerror recoveryに関する詳細はその掲載文書から省かれる。
- Haskell 2010 reportは、lexical/context-free grammarの曖昧性を最長一致・左から右の規則で解決すると明記する。layoutは単なる見た目ではなくmeaningに関係し、indentationから中間のlayout tokenを作り、明示braces/semicolonsを挿入する関数`L`でlayout-insensitive token streamへ変換する。文書はtab stopとUnicode幅の扱いも規定する。
- ECMAScriptの現行仕様は、source code pointsからlexical grammarによるinput elementsを作り、そのstreamをsyntactic grammarでparseする段階を説明する。syntactic grammarとruntime semanticsに使うgrammarも区別される。

従って「文法はEBNFで定義すればよい」と単純化できない。grammar notation、lexer/parserの結合、layoutの意味、優先順位、error production、言語版ごとの拡張を個別に記録する必要がある。

### 3.2 構文受理とwell-formedness/意味検証の境界

- LLVM IRの文書は、parserが構文的に受理する入力でも、SSA dominanceに違反してwell-formedでない例を示し、verifierを別の整形式検査として説明する。
- MLIRではTraitsがvalid IRのverification constraintsを記述し、Interfacesや一般的なpassが多様なOperationを扱うための抽象境界として説明される。これはIR固有の機能であり、通常のsource-language parserの必須機能とは限らない。
- WebAssembly Core SpecificationはValidationとExecutionを別章に分け、validation algorithmを附属資料として示す。検査条件と実行意味を別々に参照できる例である。
- AIC/0.2もtoken/syntax errorと型、CFG、SSA dominance、Phi predecessor対応等を異なる診断codeに分けている。ただし、これは現在の採用済み仕様の構造であり、他形式との比較実験による最適性の結論ではない。

ここから得た設計上の示唆は、構文解析の成功を意味検証やcodegen可能性の成功として扱わず、各検査段階の拒否理由を独立に追えるようにすることだ。どの検査を入力言語、validator、IR pass、backendのどこへ置くかは、各operationを定義する段階で確定する。

### 3.3 公開仕様と実装挙動の対応関係は文書ごとに異なる

- Python Language Referenceは構文・lexical analysis以外の説明を「読みやすい英語での説明」とし、完全に形式的な仕様ではないこと、異なるimplementationは文書外の差を持ち得ることを明記する。別に掲載されたfull grammarはCPython parser生成grammar由来であり、両者の対象は同一ではない。
- Protocol Buffers Edition 2024 language specは自身の不完全性、とくにwhitespace等のlexical detailsを明記し、手書きparserのbehaviorについてはC++ `protoc` implementationを決定源とする箇所がある。定義文書が存在することだけでは、独立parser間の完全な互換性を意味しない。
- Haskellの固定2010 reportはbaselineとして読める一方、2026-08-04のcommunity blogは改訂report作成活動を告知している。reportのみを現代処理系全体の挙動として使わず、改訂版とcompiler editionの現在地を別に追う必要がある。
- SPARQL 1.2文書はsyntax/semanticsを定義するWorking Draftで、W3C自身が作業中資料として扱うよう明記する。同じ文書のlatest RecommendationリンクはSPARQL 1.1であり、版の新しさと規範状態は別の属性である。

したがって各所見には「文書が何を定義するか」「どの実装が実際のparse/codegenに使われるか」「規範状態」「未規定部分」を添える。実装との不一致を根拠なしに仕様へ昇格せず、逆に明示された実装契約を標準一般の意味と取り違えない。

### 3.4 テキスト記法と内部/保存表現は独立に設計できる

LLVM IRはhuman-readable text、in-memory representation、on-disk bitcodeを同一semantic contentの別形式として説明する。MLIRもtext、in-memory、compact serialized formを区別する。WebAssemblyはcore moduleのbinary formatとtext formatを別章に置く。Protocol Buffersでは`.proto`定義言語と、別文書で定義されるserialization wire formatがある。

この比較から、新規compilerのAI向け入力文法、compiler内部IR、cache/transport用形式を必ず一つの符号化に統一する必要はない、という設計候補を得る。ただし複数形式を支えるとparser間の一致、canonicalization、source location、stable identity、diff round-trip、version migrationの責任が増える。AI編集の効率が上がるか、追加責務に見合うかは未検証である。

### 3.5 増分構文木編集とsource editの責任境界（Tree-sitter v0.27.2）

- releaseは2026-11-07公開、確認したtag commitは`3fb7be49145acfb07e33b61ed5689e2b6771b2e9`。公式parser文書は、piece tableやrope等の呼出側source storageを`ts_parser_parse`へ渡せると説明し、node位置をbyte offsetとzero-based row/columnで示す。生成物は句読点等の個別token nodeを持つconcrete syntax tree（CST）であり、抽象構文だけに縮約されない。
- 編集時は呼出側が変更前/後のbyte位置とpointを持つ`TSInputEdit`を作り、先に`ts_tree_edit`で旧treeのnode範囲を更新し、その編集済み旧treeを`ts_parser_parse`へ渡す。返る新treeは旧treeと内部構造を共有できる。これは再利用を可能にするAPI契約で、速度・再利用量の数値保証ではない。
- `ts_tree_get_changed_ranges`は、旧編集済みtreeと新tree間で階層的な構文構造が変わったrangeを返す。rangeは正確な文字編集範囲より少し広くなる場合がある。変更文字列そのものや意味差を返すAPIとは区別する。編集前に取得して保持していた`TSNode`を引き続き使う場合は、同じ`TSInputEdit`で`ts_node_edit`も行う。通常は編集後treeからnodeを取り直せる。
- 現行AIC parserは`parse(input: &[u8]) -> Result<Module>`で全入力を受け、newline分割・`;`以降のコメント除去・各行のlexを行う（`src/parser.rs:40-54`）。行/column spanはtokenと診断に使うが、この呼出経路には旧構文木を渡す増分parse APIも、source edit適用APIもない。これは現行実装の観測で、将来の採否判断ではない。
- 設計上は、incremental syntax reuse、source buffer／triviaの保持、意味・型の検証、永続global identityを別契約として扱う。Tree-sitterのnode再利用や位置更新は、元source textの完全round-trip、意味検証、編集をまたぐstable IDを保証する根拠にしない。これらの性能・AI局所編集品質の測定は未実施である。

各行は調査深度を保留した記録であり、対象family・言語を排除または不採用にする判断ではない。全言語・全版を通読する代わりに、次の同一論点比較で結論が変わり得る候補を選び、保留枝は参照地図へ残す。

## 5. 現行AIC設計に対する示唆

1. lexical/syntax grammar、well-formedness/type/CFG verification、target legalityを分けて記述し、それぞれのdiagnosticと受入条件を持つ。
2. input syntaxのline/indentation/token policyは暗黙にせず、AIが部分編集する際の意味変化とsource mappingを将来試験する。
3. 文書が固定版の言語規格か、更新中のreferenceか、処理系grammarか、Draftかを、調査台帳の`対象種別`と`規範状態`に記録する。
4. 新規AI入力とbackend IRを将来分ける選択肢は残しつつ、初期AIC/0.2の一形式採用を勝手に変更しない。
5. 増分parseを使う場合、source bufferとedit mapping、byte/point位置、保持済みnodeの更新責務を明示する必要がある。syntax treeの再利用だけではsource fidelity、永続ID、意味検証は定まらない。
6. これらは今後の調査・設計問いであり、AIC/0.2のAI適性、性能、全言語への優位性を示す結果ではない。
