# メモリ参照・寿命・アクセス境界の限定比較

- 調査日：2026-11-09
- 状態：特定の設計問いに対する一次資料照合（M2）。言語family全体の調査完了、AICへの機能採用、既存言語の優劣判定ではない。
- 参照母集団と深度方針：[既存言語・表現参照地図](02_既存言語・表現参照地図.md)
- 比較基準：[採用済みAIC/0.2契約](../proposals/01_初期変換契約案.md)

## 1. 問いと対象

メモリを参照する値が何を指すのか、対象の寿命と別名アクセスを何が保証するのか、範囲外アクセスをどの層がどう扱うのかを比較する。構文や構造だけでなく、言語仕様、標準libraryの安全条件、VM/IR契約を分けて読む。

AIC/0.2は純粋関数の初期契約であり、メモリ、pointer、I/O、callを含まない。この記録はその採用範囲を変更しない。参照、object、allocation、provenance、ownership等の語は形式ごとに意味が異なるため、互換語として扱わない。

今回の深度は、次に挙げる版・資料の限られた条項に限る。個別処理系、ABI、allocator、concurrency、memory ordering、FFI、全てのlibrary APIと各familyの全版は含まない。

これらは同じ「安全な参照」の別実装ではない。CとLLVMでは寿命・object・access/provenanceの制約が最適化に関係し、Rustのsafe referenceはborrowの静的契約と結び付く。JavaとPythonはobject referenceと管理対象objectを中心とし、物理layoutや回収戦略を処理系へ残す。WebAssemblyのlinear memoryはVM内のbyte範囲を守るが、その中に高級言語が構成した個別objectの有効性までは定義しない。これらは所見を並べた推論であり、用語や保証の同一性を主張しない。

## 4. 比較から得た設計上の問い

今後AICにmemory機能を提案する場合、少なくとも以下を別々に決め、意味定義と検査層を対応させる必要がある。ここでは決定していない。

1. 参照値はobject identity、typed reference、address/offset、handleのどれを表すか。nullや未初期化値はあるか。
2. allocationとlifetimeの開始・終了条件は何か。scope終了、明示free、scope cleanup、GC等をどう扱うか。
3. 有効な範囲は何で識別するか。object/array境界、byte length、alignment、型・初期化条件、one-past値をどう扱うか。
4. 読み書きの別名規則は何か。共有read、exclusive write、interior mutability、raw accessの関係を静的・動的・契約検査のどこで保証するか。
5. 無効参照、lifetime切れ、null、alignment違反、境界外accessの結果を、compile error、実行時exception/trap、明示的failure、undefined behavior相当のどれにするか。
6. 同一addressへの再allocation、pointer provenance、pointer比較、整数との変換を許すか。
7. thread/atomic/FFI/host-call/外部resourceと、object lifetime・race・cleanupをどう接続するか。

これは次段階の設計チェック項目であり、採用済み仕様への拡張ではない。現契約のmemoryなしという条件は維持する。

## 5. 今回の調査深度と保留枝

表中の再開条件はAICへの機能採用時だけに限らず、既存言語・形式間の意味比較、反例確認、参照候補自体を追加で調べる必要が出た時にも適用する。参照調査の開始とAICへの採用判断は独立している。
