# 制御フロー・効果・状態モデルの限定比較

- 調査日：2026-11-09
- 状態：**異なる設計系統の代表資料に対する特定問いの一次資料照合（M2）。全言語・全版の比較や採否決定ではない。**
- 参照母集団・資源配分方針：[既存言語・表現参照地図](02_既存言語・表現参照地図.md)
- 前段の構文・検証境界：[初回横断比較](03_入力表現・構文・検証境界比較.md)

## 1. 問い

同じ制御処理を表す時、式と文のどちらへ制御を置くか、分岐・例外・探索の遷移をどう意味づけるか、評価順と状態変更をどこまで規定するかを比べる。対象は初期AIC/0.2、C11、Rust、Haskell 2010、ECMAScript 2025、SWI-Prolog、LLVM IR、WebAssembly 3.0である。対象は命令型・純粋関数型・動的・論理型・compiler IR・VMの参照枝から共通問いに役立つ例を選んだものに限られ、どの枝も単一例で代表し尽くさない。

以下では、出典文書の記述と、そこから得た設計上の推論を分ける。現行AICについては採用契約・interpreterを確認し、外部形式については公式仕様や処理系のprimary manualを調査日現在で確認した。全実装・全方言の動作比較、benchmark、AI生成・局所修正の測定は行っていない。

## 3. 比較結果

| 対象 | 制御・結果の表現 | 効果・状態と順序 | 適用範囲・注意 |
|---|---|---|---|
| **AIC/0.2** | `br`/`br.if`でCFG edgeを指定し、各blockを一つのterminatorで閉じる。Phiは実際に通ったpredecessor edgeの値を選び、複数Phiはparallel assignmentとする。 | 採用subsetは1入力の決定的pure function。memory、call、I/O、exception、atomic/thread、nondeterminism、外部副作用を持たず、停止時の返却値だけを観測する。命令の意味・順序は固定しやすい範囲だが、未対応効果を一般に扱える設計という意味ではない。 | 初期採用範囲と現行interpreterの観測であり、後続機能の設計を決めていない。非停止loopは許可され、interpreterのfuel切れは非停止証明ではなくINCONCLUSIVE。 |
| **C11 (N1570)** | `if`/`switch`/`while`等のstatementと、条件演算子・short-circuit演算子を組み合わせる。 | side effectはexpressionの意味に現れる。一般のsubexpressionは特別に規定されない限りunsequencedであり、同じscalar objectへの特定のunsequenced side effects/value computationsはundefined behavior。対して`&&`、`||`、`?:`は左条件のshort-circuitとsequencingを明記する。 | 「Cは常に左から右」でも「未規定な順序なら常にUB」でもない。operatorごとのsequencing rule、並行atomic関係、版を確認する必要がある。 |
| **Rust Reference** | Rustはexpression中心で、`if`/`match`/block/loopもexpression。`loop`の`break`は値を返せ、label付き`break`/`continue`は対象loopを指定できる。 | Referenceはexpressionが値を作ると同時にeffectsを持ち得ること、各expression種別がoperandの評価順を定義することを記す。複数operandを持つ同Referenceの一覧対象式はsource順にleft-to-right。place/value distinction、moveやmutationも式文脈に関わる。 | 「expression言語」という一語から全operandを一律に評価する意味を仮定しない。各構文の例外的・条件付き評価を別途確認する。current Referenceの版・unstable機能までの比較は未実施。 |
| **Haskell 2010** | 通常の式評価順はdata dependencyで制約され、実装には評価順の自由がある。`IO` actionはfunctional valuesと命令的actionをつなぐMonadとして別に表される。 | `>>=`/`>>`で`IO` actionを逐次合成し、実装は指定されたaction orderを保つ義務がある。`do`はそのsequencingを命令的に見える構文で書く。`IO` actionはexceptionを返さずraiseでき、`catch`で扱う。 | Haskell 2010 Report Chapter 7の標準I/O契約に限る。後年のeffect system、async、STM、処理系のruntimeは比較していない。 |
| **ECMAScript 2025** | `break`/`continue`/`return`/`throw`などのnonlocal control transferを、仕様上のCompletion Recordのpropagationで説明する。 | Completion Recordは`[[Type]]`（normal/break/continue/return/throw）、`[[Value]]`、必要に応じたtargetを持つ。spec algorithmが突然の制御移動を段階間で伝播する意味を明示できる。 | Completion RecordはECMAScript仕様内の抽象モデルであり、実装がそのrecordをheap object等として生成するという要求ではない。Host environmentとcore languageも別文書領域。 |
| **SWI-Prolog** | predicateの複数clauseや`;`はalternative/choice pointを作り、失敗時のbacktrackingで状態を復帰して別解を探索する。cut `!`は適用範囲内のchoice pointを捨て、選択をcommitする。 | search stateのrollbackは制御意味の一部。SWI manualにはpersistent database等の変更をbacktrackableにする`undo/1`例もあり、外部・永続副作用を論理変数bindingと同じように自動で巻き戻すと仮定できない。 | この所見はSWI-Prolog Reference Manualの処理系固有説明である。Prolog言語family全体のISO適合・各実装差を示さない。 |
| **LLVM IR** | `br`はcurrent function内のbasic blockへ条件/無条件に遷移し、`ret`はreturnする。Phiは各predecessor basic blockに対応した値を、実際の流入edgeに応じて選ぶ。 | memory/call等は命令群として存在する。`invoke`のexceptional edge、landing pad、catch/cleanup padは通常のreturn/branchとは別の規則・配置制約を持つ。したがってEHを追加するloweringはnormal CFG edgeだけで閉じない。 | LLVM IRはcompiler IRの例。source-language cleanup、panic、exceptionをすべて同じ機構へlowerできるとは結論しない。current LangRefの全operation/passは未調査。 |
| **WebAssembly 3.0** | operand-stack machine上に、`block`/`loop`/`if`/`try_table`のwell-nested structured instructionを置く。branch labelはnesting depthで参照され、branchはtarget constructの外側へ抜ける。loop labelへのbranchは先頭へ戻る。 | `local.get`/`local.set`やmemory/table/global instructionsでstateを読む・更新し、各instructionのexecution semanticsが状態遷移を定義する。exception instructionは最内handlerへcontrolを移す。Validationはmoduleのwell-formednessを別に検査する。 | stack machine/structured controlの例。CFG形式との相互変換は可能でも、label depth、stack values、handler範囲、validation ruleを保存するlowering責任がある。 |

## 4. 横断して得られた設計上の示唆

以下は資料からの推論であり、AIC/0.2または後続版への採用決定ではない。

1. **制御遷移と値依存は別々に追う。** LLVM/AICのbasic block edgeとPhiはcontrol/data dependenceを露出する。WebAssemblyのnested label、ECMAScriptのcompletion, Haskell `IO` bind、Prolog choice pointはそれぞれ異なる遷移情報を運ぶ。共通内部表現にlowerする場合も、return valueだけの対応では例外・cleanup・rollback・非決定探索を保存できない。
2. **evaluation orderをoperation別に定義する。** Cのpartial sequencing、Rustの構文別評価規則、Haskellのlazy pure valuesとsequenced `IO`、AICの固定pure operationは異なる。構文の見た目やoperator名から順序を類推せず、各operationのoperand evaluation、short-circuit、副作用の観測順を意味定義に書く。
3. **state/effectをどこへ置くかを明示する。** `IO` action型、C/Rust expression effect、LLVM load/store/EH、Wasm store/control instruction、Prolog dynamic database/search stateは異なる責任配置である。将来memory、call、I/O、exception、async、nondeterminismを追加する時は、state input/output、effect sequence、failure/unwind、termination、observable resultを別々に定義する必要がある。
4. **純粋subsetは意味の境界を狭める。** 現行AICはexternal effectを外しているので、返却値・CFG・Phiだけでinterpreterとobjectを比較できる。この単純化は初期実装の特徴であり、全言語に対する適性や将来のeffect handlingの解決を示さない。
5. **未定義・非停止・探索失敗を一つのerrorへ畳まない。** Cのundefined behavior、AIC interpreterのfuel exhaustion、Prologの失敗/backtracking、ECMAScript throw、Wasm trap、LLVM poison/undefinedは異なる。各形式が持つ状態を採用時に区別し、未対応operationを黙って正常返却しない。
6. **構造化構文とCFGは違う閲覧モデルを持つ。** sourceにstructured block/regionを保つか、明示label/edgeへ早くlowerするかは独立の設計候補である。AIが修正しやすいか、CFG変換が正確かはそれぞれ局所変更・round-trip・validator・semantics試験で測る。

## 5. 今回の深度と資源上の保留

| 今回M2で照合した問い | 今回深掘りを保留した枝と理由 | 再開条件 |
|---|---|---|
| C11、Rust、Haskell、ECMAScriptの式評価・副作用順・nonlocal control | C++ object lifetime/destructor/coroutine、Ada exception/tasking、Java exception/thread、Python generator/async、各言語の全edition。共通のsequencing/control questionに絞り、runtime/library・全機能は一件ずつ通読しないため | memory/call/RAII/exception/async等の具体operationを仕様化する前に、そのoperationに関わる言語・版を再開する |
| SWI-Prologでchoice point・cut・backtracking stateがどう記述されるか | Prolog/logic languageの全処理系とSQL/SPARQL/Datalog、ASPの解探索・transaction意味。SWIの所見をlogic familyへ一般化しないため | nondeterministic operation、enumerating result API、search pruning、rollback/transactionを検討する時 |
| AIC/LLVM CFGとWebAssembly structured control/stack stateを比較 | LLVM全instruction/pass、MLIR各dialect/region interface、Wasm proposal/runtime差、GPU/OpenMP synchronization。compiler/runtime/targetの組合せが大きく、対象profileを固定してから深掘りするため | nested regions、exceptions、async, thread/GPU, indirect callsまたは別targetを追加する設計時 |
| 代表資料の明示規則を比較 | 形式的意味の全証明、各compilerのsource-to-machine correctness、AI生成・変換性能の測定は未実施。資料比較だけでは証明/benchmarkの結論にならないため | 対象機能とQA acceptance criteria、比較課題、model、参照compiler/targetをOwnerが固定した時 |

保留は候補・familyの恒久除外や不採用ではない。既存言語/formatの地図は開いたままにし、新しい機能・反例・設計判断が出た時に該当枝を着手順の先頭へ移せる。今回のSWI-Prolog、current Rust/LLVM referenceは特定問いの深さだけM2であり、当該family全体をM2に昇格させていない。
