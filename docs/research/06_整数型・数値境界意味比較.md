# 整数型・数値境界意味の限定比較

- 調査日：2026-11-09〜10
- 状態：**整数の値域・固定幅・境界演算に関する代表資料の特定問い比較（M2）。全数値体系・全言語版の調査や採否決定ではない。**
- 参照母集団と資源配分方針：[既存言語・表現参照地図](02_既存言語・表現参照地図.md)
- 前段：制御・効果・状態の意味比較：[05比較](05_制御フロー・効果・状態モデル比較.md)

## 1. 問いと対象

整数値の幅・範囲・内部的な値モデルが異なる時、加減算などの境界結果、signed/unsignedの解釈、変換の責任をどこで定めるかを比べる。採用済みAIC/0.2、C11公開draft、C++20を扱うWG21 N4861 public working draft、Ada Reference Manual 2022 Edition、Fortran 2018 J3/18-007r1 working document、ECMA-334 7th Edition (C#)、Swift Book repositoryの`swift-6.4-fcs` documentation snapshot、Rust Reference、Go 1.27 language specification、Java SE 25 JLS、Haskell 2010 Report、Python 3.15.2 Language Reference、ECMAScript 2025、LLVM IR、WebAssembly Core 3.0を対象にした。Swiftの記述は公式ガイドに限り、formal language standardとして扱わない。各行は一つの候補familyを代表しない。

中心に照合したのは固定幅加減算、overflow、integer representation、numeric conversionである。floating point、decimal/fixed-point、rational/complex、SIMD/vector、CPU instructionの全operation、全数値literal規則、性能測定、各処理系間の実行比較はしていない。以下は一次資料上の記述とそこからの設計推論を分ける。

Javaの仕様claimは版固定したJava SE 25 JLSから取り、local runは別版のOpenJDK 21.0.13 source-file launcherで行った。`javac` executableはPATHにないが、`java NumericProbe.java` source launcherによる実行はできた。JLS edition claimとJDK21実測を混同せず、他edition/JDKへ一般化しない。

public class JavaNumericProbe {
  public static void main(String[] args) {
    int maxInt = Integer.MAX_VALUE;
    long maxLong = Long.MAX_VALUE;
    int one = 1;
    long longOne = 1L;
    byte maxByte = 127;
    System.out.println("intOverflow=" + (maxInt + 1));
    System.out.println("longOverflow=" + (maxLong + 1L));
    System.out.println("intShift33=" + (one << 33));

    System.out.println("bytePromoted=" + (maxByte + 1));

## 4. 横断して得た設計上の示唆

以下は出典を比べて得た推論であり、AICの拡張仕様や採用判断ではない。

1. **整数型名だけからoverflow意味は決まらない。** `u64`ならwrapと読める言語、C/C++のsigned overflow undefined behavior、Ada signed typeのbase-range checkと別定義のmodular type、Fortranのprocessor-dependent integer kind/rangeとprocessor arithmetic条件、C#のchecked/unchecked contextsと変換別overflow、Swift Bookが説明する通常演算の停止と明示的な`&+`/`&-`/`&*` wrap、unsignedはwrapしsigned overflowは決定的に定義されるGo、Javaのlow-order-bit result、build optionでpanic/wrapが分かれる言語、無制限精度の整数、`Number`/`BigInt`の二本立て、LLVMのflag付きbitvectorが共存する。同じ`add`表記を見ても、入力側の意味を個別に確定する必要がある。
2. **計算幅と格納幅を分ける。** C/C++のinteger promotionsと整数変換、Adaのdeclared subtype range・base range・条件付き`Interfaces.Integer_n` width、Javaの`byte`/`short`/`char`→`int` numeric promotion、Goのinteger conversion時のsign/zero extensionとtruncation、Swift Bookが示す`Int`/`UInt`のplatform-native幅と明示的な型変換、ECMAScriptの数値変換のように、operandの格納型と計算規則は別の層にある。narrowing/widening、符号拡張、範囲外値をreject/wrap/saturate/trapする条件を明記しないと、境界で意味が変わる。
3. **符号はbit patternとは独立の読み方になり得る。** LLVM/WebAssemblyの同じ幅のbitvectorをunsigned compareに使うかsigned compareに使うかで結果が変わる。型検査だけでoperator選択の意味を置き換えられない。
4. **未定義・panic・trap・poison・wrap・arbitrary precision・defined signed overflowを同一の「overflow」に畳まない。** C/C++ signed arithmetic overflowのundefined behavior、Adaのbase-range overflow checkと§11.6の例外・最適化条件、Swift Bookが説明する通常演算の停止と別演算子によるwrap、Rustのbuild-dependent panic/wrap、Goの決定的signed overflow、Javaのfixed-width low-bit result、LLVMのpoison、剰余値は異なる結果である。どの結果を拒否・runtime check・trap・optimizer前提・剰余値のどれとして扱うかは、host compilerの既定値に任せず入力契約・interpreter・codegenで揃える必要がある。
5. **意味保存の最低限の境界例は型別に作る。** signed/unsignedのmin/max、その隣、`0−1`、`max+1`、literal上限超過、幅ちょうどのshift count、narrow/widen conversionを別観測する。現行AICの検査を追加・変更する指示ではなく、将来operationを増やす時の比較設計案である。
