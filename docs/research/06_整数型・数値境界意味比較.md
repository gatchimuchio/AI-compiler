# 整数型・数値境界意味の限定比較

- 調査日：2026-11-09〜10
- 状態：**整数の値域・固定幅・境界演算に関する代表資料の特定問い比較（M2）。全数値体系・全言語版の調査や採否決定ではない。**
- 参照母集団と資源配分方針：[既存言語・表現参照地図](02_既存言語・表現参照地図.md)
- 前段：制御・効果・状態の意味比較：[05比較](05_制御フロー・効果・状態モデル比較.md)

## 1. 問いと対象

整数値の幅・範囲・内部的な値モデルが異なる時、加減算などの境界結果、signed/unsignedの解釈、変換の責任をどこで定めるかを比べる。採用済みAIC/0.2、C11公開draft、C++20を扱うWG21 N4861 public working draft、Rust Reference、Go 1.27 language specification、Java SE 25 JLS、Haskell 2010 Report、Python 3.15.2 Language Reference、ECMAScript 2025、LLVM IR、WebAssembly Core 3.0を対象にした。各行は一つの候補familyを代表しない。

中心に照合したのは固定幅加減算、overflow、integer representation、numeric conversionである。floating point、decimal/fixed-point、rational/complex、SIMD/vector、CPU instructionの全operation、全数値literal規則、性能測定、各処理系間の実行比較はしていない。以下は一次資料上の記述とそこからの設計推論を分ける。

| **AIC/0.2** | `u64`は64-bit unsigned bitvectorで、値域は0〜2^64−1。booleanは別の2値型。 | `add.wrap.u64`と`sub.wrap.u64`はmodulo 2^64。literalは10進/16進をparseし、範囲外をrejectする。 | 採用済みsubsetであり、signed integer、division、shift、cast、saturating arithmeticを定義しない。 |

```java
public class JavaNumericProbe {
  public static void main(String[] args) {
    int maxInt = Integer.MAX_VALUE;
    long maxLong = Long.MAX_VALUE;
    int one = 1;
    long longOne = 1L;
```

## 4. 横断して得た設計上の示唆

以下は出典を比べて得た推論であり、AICの拡張仕様や採用判断ではない。

1. **整数型名だけからoverflow意味は決まらない。** `u64`ならwrapと読める言語、C/C++のsigned overflow undefined behavior、unsignedはwrapしsigned overflowは決定的に定義されるGo、Javaのlow-order-bit result、build optionでpanic/wrapが分かれる言語、無制限精度の整数、`Number`/`BigInt`の二本立て、LLVMのflag付きbitvectorが共存する。同じ`add`表記を見ても、入力側の意味を個別に確定する必要がある。
2. **計算幅と格納幅を分ける。** C/C++のinteger promotionsと整数変換、Javaの`byte`/`short`/`char`→`int` numeric promotion、Goのinteger conversion時のsign/zero extensionとtruncation、ECMAScriptの数値変換のように、operandの格納型と計算規則は別の層にある。narrowing/widening、符号拡張、範囲外値をreject/wrap/saturate/trapする条件を明記しないと、境界で意味が変わる。
3. **符号はbit patternとは独立の読み方になり得る。** LLVM/WebAssemblyの同じ幅のbitvectorをunsigned compareに使うかsigned compareに使うかで結果が変わる。型検査だけでoperator選択の意味を置き換えられない。
4. **未定義・panic・trap・poison・wrap・arbitrary precision・defined signed overflowを同一の「overflow」に畳まない。** C/C++ signed arithmetic overflowのundefined behavior、Rustのbuild-dependent panic/wrap、Goの決定的signed overflow、Javaのfixed-width low-bit result、LLVMのpoison、剰余値は異なる結果である。どの結果を拒否・runtime check・trap・optimizer前提・剰余値のどれとして扱うかは、host compilerの既定値に任せず入力契約・interpreter・codegenで揃える必要がある。
5. **意味保存の最低限の境界例は型別に作る。** signed/unsignedのmin/max、その隣、`0−1`、`max+1`、literal上限超過、幅ちょうどのshift count、narrow/widen conversionを別観測する。現行AICの検査を追加・変更する指示ではなく、将来operationを増やす時の比較設計案である。

## 5. 今回の深度と資源上の保留

| 今回M2で照合した問い | 深掘りを保留した枝と理由 | 再開条件 |
|---|---|---|
| AIC/0.2/C11/C++20 N4861/Rust/Go 1.27/Java SE 25のinteger range・overflow・promotion、Haskell/Python/ECMAScriptの数値幅モデル、LLVM/Wasmのbitvector演算 | C++はN4861 public draftだけで、最終ISO/IEC 14882:2020本文・他edition・他compilerは未照合。Ada、Fortran、C#、Swift、Zig、各DSL/SQL numeric typeは、変換・overflow・literal・promotion規則が別々で、共通operation/questionを固定した後に比較するため。各family全体はM0の候補地図に残す。Go implementation behaviorとJavaのother JLS/JDKも未観測 | 各languageのother edition/JDK/runtime、C++の最終ISO版/target compiler、その他のsigned/unsigned type、multiply/divide/shift/cast、checked/saturating arithmeticをAIC仕様化またはtarget loweringする前に該当版・処理系を追加 |
| integerのみ。floating-point、decimal、fixed-point、rational、complex、vector/SIMD、NaN/rounding/contractionは未確認 | これらはprecision、rounding mode、exception flag、library/runtime、target featureが整数のmodulo/range比較より広く、別調査問いとして台帳化するため | 対応numeric type、literal、conversion、target featureのいずれかを採用候補にする時 |
| language/IRの算術値とsource-level conversion。形式のwire encodingやABI marshallingは比較していない | Protobuf/ASN.1/CBOR、SQL numeric、FFI、C ABI/LLVM data layoutのnumeric representationは、算術値と保存・伝送形式が別課題のため | serialized field、foreign call、memory layout、numeric ABIを追加する時 |

保留は枝や候補の恒久除外・不採用ではない。参照母集団を開いたままにし、機能案や反例が出た時は再開条件に従い当該言語・形式を調査順の先頭へ移す。今回M2なのは記載した整数の問いだけであり、C/C++/Rust等のfamilyやその版全体ではない。
