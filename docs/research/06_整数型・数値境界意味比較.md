# 整数型・数値境界意味の限定比較

- 調査日：2026-11-09
- 状態：**整数の値域・固定幅・境界演算に関する代表資料の特定問い比較（M2）。全数値体系・全言語版の調査や採否決定ではない。**
- 参照母集団と資源配分方針：[既存言語・表現参照地図](02_既存言語・表現参照地図.md)
- 前段：制御・効果・状態の意味比較：[05比較](05_制御フロー・効果・状態モデル比較.md)

## 1. 問いと対象

整数値の幅・範囲・内部的な値モデルが異なる時、加減算などの境界結果、signed/unsignedの解釈、変換の責任をどこで定めるかを比べる。採用済みAIC/0.2、C11公開draft、Rust Reference、Haskell 2010 Report、Python 3.15.2 Language Reference、ECMAScript 2025、LLVM IR、WebAssembly Core 3.0を対象にした。各行は一つの候補familyを代表しない。

中心に照合したのは固定幅加減算、overflow、integer representation、numeric conversionである。floating point、decimal/fixed-point、rational/complex、SIMD/vector、CPU instructionの全operation、全数値literal規則、性能測定、各処理系間の実行比較はしていない。以下は一次資料上の記述とそこからの設計推論を分ける。

## 3. 比較結果

| 対象 | 型と値域 | 境界演算・変換 | 適用範囲・注意 |
|---|---|---|---|
| **AIC/0.2** | `u64`は64-bit unsigned bitvectorで、値域は0〜2^64−1。booleanは別の2値型。 | `add.wrap.u64`と`sub.wrap.u64`はmodulo 2^64。literalは10進/16進をparseし、範囲外をrejectする。 | 採用済みsubsetであり、signed integer、division、shift、cast、saturating arithmeticを定義しない。 |
| **C11 (N1570)** | 標準integer typesの幅・rankは型規則と実装範囲で定まる。exact-width typedef (`uint64_t`等)は存在が保証される型ではない。signed representationはsign-and-magnitude、two's complement、ones' complementのいずれかが実装定義。integer promotionsで、source objectの格納幅とoperatorの計算型が異なる場合がある。 | unsigned演算結果が型の表現範囲を超える場合、最大値+1を法としてreductionする。signed演算結果がその型の値域外になる例外条件はundefined behavior。signed bitwise操作は表現依存またはundefinedな部分があり、shift countの条件も個別に規定される。 | 「変数の幅をそのまま演算幅とする」とは限らない。どの型へinteger promotionされたか確認する。N1570の対象版・draft状態に限定する。 |
| **Rust Reference** | `u8`〜`u128`、`i8`〜`i128`の明示幅と値域がある。signed型はtwo's complement。`usize`/`isize`はpointer幅依存。 | builtin integer operatorのoverflowはdebug modeでpanicする。`-C debug-assertions`/`-C overflow-checks`が確認・動作を制御し、他buildでのoverflowは実装がpanicまたはwrapを選び得る。明示的wrap/checked/saturating APIも別にある。 | language type range、compiler flag、standard-library APIを同じ契約としてまとめない。版・build条件を付けて読む。 |
| **Haskell 2010** | Preludeの`Int`はfixed-precisionで最低値域を持ち、正確な上下限は`minBound`/`maxBound`で得る。`Integer`はarbitrary-precision。 | §6.4はfixed-precision numeric typesのoverflow等のexceptional resultについて、実装がerror/bottom、truncated value、special value等を選べると記す。§18.1 `Data.Int`は同moduleのsigned integer arithmeticをmodulo 2^nと明記する。 | core numeric classの一般記述とlibrary moduleの記述を分ける。実装固有の`Num` instanceや全演算へ、一方だけから一般化しない。 |
| **Python 3.15.2** | `int`はunlimited precision。boolはintのsubtype。組み込み`float`/`complex`は別の数値型で、整数とのmixed arithmetic規則も仕様にある。 | integer bitwise結果は、無限個のsign bitを持つtwo's-complement表現で計算したかのように定義する。bitwise shiftにnegative countを与えると`ValueError`。 | integer幅によるwrapを前提にしない。unlimited precisionは使用可能メモリ等の実装資源が無限という意味ではない。 |
| **ECMAScript 2025** | numeric typeを`Number`と`BigInt`に分ける。`Number`はIEEE 754 binary64で、全整数が連続して正確に表せるsafe rangeは−(2^53−1)〜2^53−1。`BigInt`は固定bit-widthに制限されない。 | `Number`はbinary64演算、`BigInt`は原則として数学的に正確な整数演算。numeric type間に暗黙の一般変換はなく、`BigInt` operandへ`Number`を暗黙変換する通常の算術はTypeErrorになる。 | `Number`では±2^53自体も表現可能だが、隣接する全整数の識別を保証する範囲とは別。32-bit typed conversion等も別のabstract operationとして範囲へ変換する。 |
| **LLVM IR** | `iN`はN-bit integer valueで、signednessは型名で固定せずoperationの解釈に現れる。 | `add`等はN-bit resultを作る。`nsw`/`nuw`なしではmodulo bitvector結果。flagを付けて該当するsigned/unsigned overflowが起きるとresultはpoisonとなる。 | poisonは直ちにtrapする値と同じではない。flagはsource-language前提を表すので、loweringがsourceのoverflow semanticsを正しく証明/保持する必要がある。 |
| **WebAssembly 3.0** | `i32`/`i64` valuesはbitvector。signed/unsigned interpretationはcomparison/division等のoperationにより選ぶ。 | `add`/`sub`/`mul`はmodulo 2^N。shiftはcountをNでmoduloしてから適用する。division等は別個のexception/result ruleを持ち、addのwrap ruleを適用しない。 | Wasm core instruction semanticsに限定。embedding/APIや別proposalのnumeric types、各source-language loweringは未調査。 |

## 4. 横断して得た設計上の示唆

以下は出典を比べて得た推論であり、AICの拡張仕様や採用判断ではない。

1. **整数型名だけからoverflow意味は決まらない。** `u64`ならwrapと読める言語、build optionでpanic/wrapが分かれる言語、無制限精度の整数、`Number`/`BigInt`の二本立て、LLVMのflag付きbitvectorが共存する。同じ`add`表記を見ても、入力側の意味を個別に確定する必要がある。
2. **計算幅と格納幅を分ける。** Cのinteger promotionsやECMAScriptの数値変換のように、operandの格納型と計算規則は別の層にある。narrowing/widening、符号拡張、範囲外値をreject/wrap/saturate/trapする条件を明記しないと、境界で意味が変わる。
3. **符号はbit patternとは独立の読み方になり得る。** LLVM/WebAssemblyの同じ幅のbitvectorをunsigned compareに使うかsigned compareに使うかで結果が変わる。型検査だけでoperator選択の意味を置き換えられない。
4. **未定義・panic・trap・poison・wrap・arbitrary precisionを同一の「overflow」に畳まない。** 失敗結果を拒否、runtime check、trap、optimizer前提、剰余値のどれにするかは、host compilerの既定値に任せず入力契約・interpreter・codegenで揃える必要がある。
5. **意味保存の最低限の境界例は型別に作る。** signed/unsignedのmin/max、その隣、`0−1`、`max+1`、literal上限超過、幅ちょうどのshift count、narrow/widen conversionを別観測する。現行AICの検査を追加・変更する指示ではなく、将来operationを増やす時の比較設計案である。

## 5. 今回の深度と資源上の保留

| 今回M2で照合した問い | 深掘りを保留した枝と理由 | 再開条件 |
|---|---|---|
| AIC/0.2/C11/Rustのfixed-width integer rangeとoverflow、Haskell/Python/ECMAScriptの数値幅モデル、LLVM/Wasmのbitvector演算 | C++、Go、Ada、Fortran、Java、C#、Swift、Zig、各DSL/SQL numeric typeは、変換・overflow・literal・promotion規則が別々で、共通operation/questionを固定した後に比較するため。family全体M0の候補地図には残す | signed/unsigned type、multiply/divide/shift/cast、checked/saturating arithmeticをAIC仕様化またはtarget loweringする前に、該当言語・版を追加 |
| integerのみ。floating-point、decimal、fixed-point、rational、complex、vector/SIMD、NaN/rounding/contractionは未確認 | これらはprecision、rounding mode、exception flag、library/runtime、target featureが整数のmodulo/range比較より広く、別調査問いとして台帳化するため | 対応numeric type、literal、conversion、target featureのいずれかを採用候補にする時 |
| language/IRの算術値とsource-level conversion。形式のwire encodingやABI marshallingは比較していない | Protobuf/ASN.1/CBOR、SQL numeric、FFI、C ABI/LLVM data layoutのnumeric representationは、算術値と保存・伝送形式が別課題のため | serialized field、foreign call、memory layout、numeric ABIを追加する時 |

保留は枝や候補の恒久除外・不採用ではない。参照母集団を開いたままにし、機能案や反例が出た時は再開条件に従い当該言語・形式を調査順の先頭へ移す。今回M2なのは記載した整数の問いだけであり、C/C++/Rust等のfamilyやその版全体ではない。
