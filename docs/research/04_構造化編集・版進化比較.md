# 構造化編集と版進化の限定比較

- 調査日：2026-11-09
- 状態：**選択した表現の特定問いに対する一次資料照合（M2）。母集団の網羅、編集性能測定、形式の採否ではない。**
- 参照母集団と深度方針：[既存言語・表現参照地図](02_既存言語・表現参照地図.md)
- 前段の構文・検証境界：[初回横断比較](03_入力表現・構文・検証境界比較.md)

## 1. 問いと前提

AIが既存プログラムや定義の一部分だけを変更するとき、どの単位を参照して変更するか、変更後に意味の一貫性をどう検査するか、形式の更新で既存データ・古い利用者・コメントなどをどう扱うかを比較する。対象は、採用済みAIC/0.2、JSONとJSON Schema 2020-12、YAML 1.2.2、Protocol Buffersの定義言語とwire-format進化である。これは全ての言語・版を代表するものではなく、既存言語・形式の広い参照母集団は引き続き開いておく。

規格・仕様が定めるデータモデルと、編集器が原文をどれほど保持できるかは別の問題である。以下では資料の明文と、そこから得た設計上の推論を分ける。AIC/0.2は現行契約とこのrepositoryの実装を確認し、外部形式は公式仕様・一次資料を調査日現在で照合した。AIによる編集精度、修正成功率、token/resource消費の比較実験は行っていない。

## 3. 比較結果

| 形式 | 局所編集の参照単位・識別 | 順序・原文保持 | 版進化・未知要素 |
|---|---|---|---|
| **AIC/0.2** | 物理1行に宣言・命令・block label・terminatorを置く。`%value`と`^block`で定義・参照を明示し、value IDとblock IDは各々module内で一意。Phi入力は実際のpredecessor blockを明示する。構文上のIDは一つのmoduleの内部名であり、版をまたいで維持される永続IDの規則はない。 | 1行単位は構文レコードとして明示される。parserはline/byte-columnを診断に使う。意味を保ったまま任意の整形・並べ替えをする仕組みや原文コメントを保持するround-trip契約は定義されていない。 | headerは厳密に`0.2`のみを受理し、別versionは`E_VERSION`。migrationやunknown operationの保存は定義せず、unsupported operationは拒否する。初期subsetとしての厳格さであり、一般形式に対する採否ではない。 |
| **JSON (RFC 8259)** | objectはname/value pairのunordered collection、arrayはordered sequence。object member名はuniqueであるべき（SHOULD）で、重複時の受信側挙動は予測不能とされる。JSONのデータモデル自体にpersistent node IDはない。 | objectのテキスト上の順序は意味として保証されず、array順は意味に含まれる。RFCのデータ構造にはcomment要素やsource locationがない。これらが必要な編集器は別の具体構文・source map層を用意する必要がある、というのは設計上の推論。 | JSON自体は外部schemaやversion migrationを規定しない。object propertyを追加・削除したときの互換性は、利用者とschema契約が定める。duplicate nameを許容するparser差は曖昧な意味を残すため、採用側で拒否境界を定める必要がある。 |
| **JSON Schema 2020-12** | `$schema`はdialectとそれを定義するmeta-schema resourceのURI識別子、`$id`はschema resourceのcanonical URI。JSON instance内の任意ノードに永続IDを付ける機構とは異なる。 | JSONのvalue treeを検査するschema層であり、コメント・空白や既存の原文を保存する編集形式ではない。 | `properties`や`additionalProperties`等で拡張propertyを許す/制限する方針を記述できる。`additionalProperties`を省略したときは空schemaと同じassertion動作であり、未知propertyを一律拒否しない。`unevaluatedProperties`やrequired constraintsも使えるため、strictnessは明示的に設計できる。vocabulary/dialect識別を通じて拡張を表せるが、validatorが未知の仕様を意味まで理解する保証にはならない。 |
| **YAML 1.2.2** | representationはtagged nodeからなるgraphで、共有ノード・cycleを含み得る。mappingのkey/value集合はunorderedでkeyはunique、意味のある順序はsequenceで表す。anchor/aliasはserialization上の共有参照表現だが、永続的なnode IDの契約ではない。 | specificationはcomment、indentation、node style、mapping key order等をpresentation/serialization detailとして区別し、commentはnodeに紐付かない。semantic valueだけの再出力では人が書いたコメント・並び・styleを保持する保証はない。保持する編集器は具体構文情報を別途保持すべき、というのは設計上の推論。 | `YAML 1.2.2`は言語仕様版であり、個々のconfiguration schemaやapplication versioningを定めるものではない。異なるprocessorのscalar resolution等を含む実装差、schema ecosystem全体の互換性は今回未調査。 |
| **Protocol Buffers** | `.proto`のfield numberはwire formatでfieldを識別し、message内で一意。field number変更・再利用は危険で、削除した番号を`reserved`にする。必要に応じてJSON/TextFormat向けに削除済みfield名もreserveする。 | `.proto`でfieldを記述する順序はserializationに影響しない。messageのfield serialization orderは保証されず、implementation detailとされる。従ってwire bytesの一致を意味の同一性とみなせず、source順も恒久のidentityにできない。 | 新fieldには未使用のfield numberを割り当て、削除済みnumberを墓標として保持する運用規則がある。wire typeにより旧parserが未知fieldをskipできる一方、field number/typeの変更や再利用には互換性上の危険がある。schema source、binary wire format、JSON/TextFormatを分けて考える必要がある。 |

## 4. この比較から得る設計上の示唆

ここからの項目は設計候補・問いであり、AICの変更決定ではない。

1. **意味上のidentityと編集用identityを分ける。** AIC/0.2のvalue/block名、JSON object key、JSON Schemaのresource URI、Protobuf field numberはそれぞれ適用範囲が異なる。AICの名前やJSON/YAMLの位置をrevision間の不変IDと推定しない。局所編集とdiff mergeを要件化するとき、永続IDを持たせるか、名前変更を参照更新として扱うか、移動後も同じ要素とみなす条件を定める。
2. **意味構造と原文保持を別の層で考える。** JSON/YAMLのdata modelとAICのsemantic/IR構造からはcomment・空白・元の表記が失われ得る。編集結果を人が読む必要があるか、元ファイルを最小diffで保つ必要があるかを確認し、必要ならconcrete syntax tree/token/source spanをsemantic modelと並行して保持する。これはround-tripの責任を増やすため測定対象とする。
3. **順序は形式ごと・構造ごとに定義する。** JSON/YAML object/mapのmember順はsemantic orderとして使えないが、array/sequenceは順序を持つ。AIC instruction/block順やProtobuf schema declaration順もそれぞれの意味・wire規則に照らして扱う。人間が見た順序を意味順と仮定しない。
4. **未知要素とschema evolutionを先に選ぶ。** 固定subsetのAIC/0.2は未知operationを拒否する。JSON Schemaはunknown propertyへの許可・拒否をconstraintsで記述し、Protobufはtag付き未知wire fieldをskip可能にする。将来拡張で「拒否」「保持して再出力」「無視」をどれにするかは、入力誤り検出、forward compatibility、lossless editの間の選択になる。
5. **version pinningとmigrationは別に記録する。** AICの厳密な`0.2` header、JSON Schemaの`$schema` dialect URI、YAML spec edition、Protobuf editionsは同じversioning機構ではない。形式版、文法版、schema/application版、保存wire version、migration policyをひとつの番号に押し込まない。
6. **互換性は編集テストで測る。** AIに同じ局所変更課題を与えて、意味差分、触れた行数/bytes、参照一貫性、comment保持、parse/validation後の回復、version update結果、token/resource costを測る必要がある。比較候補、model、課題set、score rule、acceptance thresholdはOwner判断とQA計画に従って決める。文書仕様の読解だけから優位形式を断定しない。

## 5. 今回の深度と資源上の保留

| 今回M2で確認した問い | 今回深掘りを保留した枝と理由 | 再開条件 |
|---|---|---|
| AIC/0.2、JSON、YAML、Protobufで順序・参照識別・comment/source fidelity・schema evolutionがどう定義されるか | XML/XSD、CBOR/ASN.1、Avro、Thrift、Cap'n Proto、FlatBuffers等の個別版・processor差。データ/schema familyには規格・版・encodingの組合せが多数あり、同じ共通質問を固定してから比較しないと枝ごとの確認量が増えるため | binary edit、unknown-field round-trip、生成schema/API compatibility、signed/canonical payload等の選択が必要になった時に該当branchを先行し、公式版・processorと同じ質問で照合する |
| JSON Schema 2020-12でdialect/resource identityとunknown property policyがどう結び付くか | JSON Schemaの全vocabulary、all validator implementation、migration ecosystem。今回の資源配分では、共通問いに関係するdialect/unknown-propertyの規則を先に照合し、残りの網羅確認は保留する | AIC input schemaやextension ecosystemを追加設計する時、または互換性宣言でvalidator差が問題になる時 |
| Protobuf Edition guideでfield number reservationとwire serialization orderを確認 | wire unknown field preservationのruntime別の挙動、全edition/proto2/proto3 migration表、source round-trip実装。guide記述を全実装の等価な保証へ広げないため | interop/runtime compatibilityを採用判断に使う時。使用言語・compiler・runtime・editionを固定した試験を行う |

保留は参照枝の削除、恒久除外、または形式の不採用を意味しない。形式の追加、調査順、branch深度は、新たな設計判断に効く根拠と利用可能な資源を見て更新する。個々の言語・formatに対する未調査項目は[参照地図](02_既存言語・表現参照地図.md)のM0/M1に残す。
