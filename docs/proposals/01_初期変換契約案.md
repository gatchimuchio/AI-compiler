# 初期変換契約の採用候補

- 作成日：2026-11-09
- 状態：**Owner未採用の設計案。現行仕様・target選定・R3実装許可ではない。**
- 根拠：docs/research/01_既存技術・規格調査.md

## 1. 候補の要約

版管理された小さなAI操作文字列を意味検査し、basic block表現から指定target向けELF relocatable objectへ変換する。sourceは単一の引数なし関数mainを定義し、u64を返す。初期版にmemory、external call、I/O、system callを含めない。

| 項目 | 推奨候補 | 状態 |
|---|---|---|
| source契約 | AIC/0.1、u64/bool、CFG、phi、return | 未採用 |
| 第一target候補 | Linux x86-64 System V ABI、LP64、ELF64 ET_REL | 未採用。ISA一次資料待ち |
| 比較target候補 | Linux AArch64、AAPCS64/AAELF64 2026Q3、ELF64 ET_REL | 未採用。ISA一次資料待ち |
| compiler実装言語 | Rust 2024 edition、stable toolchain固定、Cargo | 未採用。toolchain未導入 |
| object生成 | 対象assemblyを自前生成しGNU asでET_REL化 | 未採用 |
| linker | compiler本体は呼ばない。試験harnessとの結合時のみ使用 | 未採用 |

## 2. Target候補の比較

| 観点 | Linux x86-64 | Linux AArch64 |
|---|---|---|
| ISA profile | AMD64/x86-64 baseのみ。optional extensionsなし。正確なvendor manual版・命令条件は採用前に固定 | AArch64/Armv8-A baseのみ。SIMD/SVE/PAuth等なし。Arm ARMの版とfeature条件は採用前に固定 |
| ABI | System V AMD64 ABI supplement v1.0のLP64。x32/ILP32を除く | AAPCS64 2026Q3基本integer PCS。Linux platform-specific supplementを実装前に固定 |
| OS境界 | Linux userspace内の関数object。generated functionからsyscallを禁止。外部harnessが通常ABIで呼ぶ | 同じく関数objectとし、初期sourceからsyscallを禁止 |
| object | ELF64 x86-64 ET_REL。初期はundefined external symbol、data section、relocationを生成しない。aic_mainはexportする | ELFCLASS64 / EM_AARCH64 / ET_REL。undefined external symbol、data section、relocationなし。aic_mainをexportする |
| 互換性 | Linux x86-64環境で利用できる範囲が広く、現環境でhost実行可能 | Linux AArch64も広く利用される。optional CPU featureの扱いを固定する必要がある |
| 実装負荷 | 可変長encodingとfeature差は複雑。assemblerへencodingを委譲すれば初期backendを限定できる | 固定長A64命令は基礎命令のencodingが扱いやすい。一方Linux cross toolchainが現環境にない |
| 検証 | 現環境はx86_64、GCC 14.2.0、GNU as/ld 2.44、readelf、objdumpを確認 | AAPCS64/AAELF64を確認。cross as/ld、QEMUは未導入。AArch64 hardwareまたはuser-mode emulatorが必要 |
| 保守 | Intel/AMD間で共通する必須baselineとOS/ABIを明示する | Arm CPU間で共通するbaselineとLinux platform ABIを明示する |
| 暫定評価 | 現環境でtargeted試験を行えるため第一候補 | ABI/ELF資料は確認できたがISA資料と検証設備を補う必要がある |

両候補ともSystem V/Arm ABIがISA仕様を代替しない。Intel SDMまたはAMD APM、Arm ARM、System V gABIへの接続が戻った後に候補profileを再照合する。

## 3. AIC/0.1入力候補

### 3.1 Grammar

ASCII行指向形式。識別子は小文字英字で始まり、後続に小文字英数字とunderscoreを許す。空白・改行はseparator。未知のversionは拒否する。target profileはsourceに含めず、compile inputとして明示する。

    module       = header, function
    header       = "AIC", version
    function     = "fn main() -> u64 {", block+, "}"
    block        = block_label, instruction*, terminator
    instruction  = const | add | sub | eq | phi
    const        = value_id, "= const.u64", integer
    add          = value_id, "= add.wrap.u64", value_id, value_id
    sub          = value_id, "= sub.wrap.u64", value_id, value_id
    eq           = value_id, "= eq.u64", value_id, value_id
    phi          = value_id, "= phi.u64", predecessor_value+
    terminator   = "br", block_label
                 | "br.if", bool_value, block_label, block_label
                 | "ret.u64", value_id
    value_id     = "%", identifier
    block_label  = "^", identifier
    integer      = decimal_digits | "0x", hexadecimal_digits

versionは数字.数字、identifierは小文字英字から始まるASCII小文字/数字/underscore列とする。integerは0から2^64-1の範囲に限る。commentとescape sequenceはAIC/0.1にはない。

### 3.2 Example

    AIC 0.1
    fn main() -> u64 {
    ^entry:
      %two = const.u64 2
      %three = const.u64 3
      %five = add.wrap.u64 %two %three
      %expected = const.u64 5
      %ok = eq.u64 %five %expected
      br.if %ok ^yes ^no
    ^yes:
      %answer = const.u64 42
      br ^join
    ^no:
      %fallback = const.u64 0
      br ^join
    ^join:
      %result = phi.u64 [^yes %answer] [^no %fallback]
      ret.u64 %result
    }

このsourceの定義済み結果は42。block、値、型、CFGを検査してからtarget依存処理へ進む。

### 3.3 Semantics and validation

- moduleはversionを宣言する単一関数mainだけを含み、引数なし、戻り値u64。
- u64は0から2^64-1までの64-bit unsigned bitvector。add.wrap.u64とsub.wrap.u64はmodulo 2^64。host言語のoverflowやCのundefined behaviorに委ねない。
- eq.u64はu64どうしを比べboolを返す。br.ifはtrue/falseでbranchする。phi.u64は制御が到達したpredecessor labelで値を選ぶ。入力の並び順に実行意味を与えない。
- SSA valueは一度だけ定義し、useは定義が到達する場所にあり、型が一致しなければならない。labels/value IDsは一意、branch targetは存在し、各blockは一つのterminatorで閉じ、phiはblock先頭に置く。phi入力はCFG predecessor各edgeに揃える。
- loopを含む全CFGを扱い、停止しない実行は非停止として定義する。reference interpreterのfuel上限到達は停止証明やcompiler成功を意味しない。
- source version、target profile、compiler versionを分離する。targetをhostから推測しない。未知version、target不一致、未対応op、検証不能は成功扱いにしない。

### 3.4 初期版で拒否する操作

memory read/write、pointer、array、global/data section、function arguments、複数関数とcall、I/O、system call、float、vector/SIMD、atomic、thread、exception、inline assembly、undefined/poisonを含めない。heap、文字列、object layout、OS APIも対象外。安定error codeを返しobjectを出力しない。

## 4. Sourceからobjectまでの変換経路

1. **Parse:** AIC versionと構文を読み、位置付き診断を作る。未知命令/version、重複定義、欠落terminatorを拒否する。
2. **意味検査:** 型、SSA single assignment、dominance、CFG predecessor、phi incoming edge、return型を検査する。失敗時にartifactを作らない。
3. **Target非依存IR:** u64定数/加減算/比較、block/branch/phi/returnだけを保持する。AI sourceの意味をここで確定する。LLVM IRを必須依存や正本にしない。
4. **Target profile:** ISA/base features、ABI/data model、Linux userspace、ELF class/machine/type、toolchain identityを明示確認する。host CPUからの暗黙選択をしない。
5. **Instruction selection:** 最初の簡易実装候補は各SSA値に8-byte stack slotを割当て、scratch/caller-saved registersだけを使う方式。branch edgeでphi入力を対応slotへcopyする。full register allocatorを先送りする代わりに速度・小さいobjectを目標にしない。frame上限（例：64 KiB）はOwner承認を要する候補値。
6. **ABI function emission:** objectにaic_main symbolを出し、引数なし/u64戻り値とする。x86-64ではSystem V ABIの整数戻り値register、AArch64ではAAPCS64のresult registerを使う。callee-saved registerを壊さず、frame size/alignment/returnをtarget別に検査する。
7. **Assembler:** compilerはassemblyを決定的に出し、GNU asを明示targetで実行してET_REL objectを作る。未解決symbol、assembler failure、禁止relocation時は失敗し、部分artifactを成功結果にしない。
8. **Object inspection:** readelfまたは検査器でELF class、endianness、e_machine、ET_REL、section flags、symbol、relocationを照合する。objdump -drをレビューに使う。object検査自体は意味保存証明ではない。
9. **Functional test:** test専用harnessがobjectのaic_mainを通常ABIで呼んでu64結果を比較する。harnessのCは呼出側に限り、AI入力をCへ変換しない。compiler自身はlinkerを呼ばない。standalone startup/runtime/executableは後続判断にする。

どの段階の不正入力、未対応target/op、tool失敗、ELF不整合も成功artifactにしない。

## 5. 言語・build・assembler/linker案

### 実装言語候補：Rust 2024 / Cargo

Typed AST、CFG、SSA validator、target profile、stable error enumを型で表せる。最初はRust standard libraryのみとし、外部crateを避けて依存とlockfileを小さくする。stable rustcとCargo versionをtoolchain fileで固定し、build optionとartifact namingを記録する。

Rustでも意味保存は自動証明されない。各parser/validator/interpreter/backend境界の検査が必要。現環境ではrustc/cargoがPATHになく、build・toolchainは未検証。Owner採用後に公式配布から導入してversion/hashを固定する。

**代替：** OCaml+CoqはCompCertの証明・抽出方式に近く、形式証明の道筋があるがproof開発、Coq依存、出力保証の検査も必要で初期負荷が大きい。C/C++は現環境で始めやすい一方、所有権・範囲安全の管理負荷が増え、GCC/LLVM IR採用の必要性は生じない。

### GNU assemblerを使いlinkerを分離

小さい整数subsetの初期版では、assemblyからET_RELを作る既存GNU asの利用を候補とする。命令encoding/assembler relocationを委ねるが、source semantics、命令選択、ABI、assemblyの正当性に対するcompiler責任は残る。assemblerの受理をcorrectness proofと扱わない。

compiler本体ではlinkerを起動しない。外部C harnessとの結合は受入試験の別段階。独自ELF/relocation writerを早期に作ると目的外のformat実装が増えるため保留する。standalone executable、startup code、runtime、linker flagsは別途採用が必要。

## 6. 受入予定試験

| 性質 | 試験案 | 判定と限界 |
|---|---|---|
| 意味保存 | 独立AIC interpreterと生成objectを呼ぶharnessを、定数/算術/比較/分岐/phi/停止loop fixtureで比較 | 停止fixtureの全期待u64値が一致。interpreter自体は別検証し、有限suiteを証明と称さない。 |
| 算術境界 | 0、1、2^64-1、加減算wrap、eqのtrue/false | 定義済みbitvector意味と一致。未実行値をPASSにしない。 |
| ABI/ELF | readelfでclass/type/machine/section/symbol/relocation確認。harnessで戻り値とcallee-saved registerを検査 | 対象版・実行環境ごとにassertionが実行・成功。全CPU/OSへの一般化なし。 |
| 決定性 | 同じsource/profile/compiler/toolchainで二回生成したobjectをSHA-256比較 | byte-for-byte一致。timestampと作業directoryを埋め込まない。toolchain版をまたぐ一致は別保証。 |
| 拒否 | malformed/version、unknown/duplicate value、型違い、bad phi/target、terminator不足、unsupported op/profile、frame limit超過 | 安定error code、nonzero status、objectなし。各条件のnegative fixtureが必要。 |
| 誤った成功なし | unsupported op、assembler failure、unresolved relocationを故意に入力 | 呼出可能objectを出さず、既存artifactを成功物で上書きしない。 |

候補Aはx86_64 hostで試験し、候補Bはcross toolchainとAArch64 hardwareまたはQEMU user-modeで同一suiteを実施する。リポジトリには現在compiler/test runnerがないため、これらの試験は全て未実施。

## 7. Ownerの採用が必要な事項と停止境界

1. AIC/0.1のgrammar、u64 wrap semantics、phi/CFG条件、unsupported list。
2. 初期targetとISA版、必須features、Linux platform ABI、ELF gABI版。ISA一次資料を再調査した後に選ぶ。
3. Linux関数objectだけを受入対象にし、memory/call/syscall/standalone executableを初期範囲から外すこと。
4. Rust 2024/Cargoと外部crateを使わない方針。
5. GNU as、ET_REL出力、compiler本体でlinkerを呼ばない方針。
6. 初期QA、AArch64検証環境、性能目標を初期受入に含めるか。
7. compilerとtoolchainの最終license/配布方針。

文法の曖昧さ、意味定義、変換stage、拒否条件、検査案は調査・提案としてCodexが引き続き具体化できる。Owner採用前はtargetを正式決定せず、R3実装、性能、ISA適合を主張しない。
