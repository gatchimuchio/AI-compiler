## 1. 旧案の監査結果と採用記録

前版AIC/0.1は、そのまま実装仕様として使える状態ではなかった。文法にブロック末尾のコロン、token境界、行コメントと空白規則が揃わず、可変長Phiの記法・型検査・前駆辺との一対一対応も定義不足だった。例は引数のない固定値計算に留まり、入力依存の計算とAI操作形式としての利点を示していなかった。Phi loweringは複数値の同時代入やコピー循環を説明しておらず、Linux ELFとWindows PE-COFFの同じ尺度での比較も不足していた。

今回、相互に整合する候補として提示したAIC/0.2の初期範囲をOwnerが2026-11-09に採用した。AIC/0.1は過去の未採用案として履歴に残し、0.2との互換性を主張しない。以前の「すべて未採用」という記述はこのOwner採用により置き換わった。比較案、未確認規格、将来機能、品質閾値、公開判断は引き続き未採用である。

**Owner採用記録（2026-11-09）：** AIC/0.2、`aic_main(u64) -> u64`、Linux x86-64/System V ABI/ELF64 ET_RELのみ、compilerはRust 2024 + Cargo、object組立にGNU as、linkerは試験harness側のみ、memory/I/O/callなし。普及率を重視する追加指示に対する「どっちも採用」は、Rustをcompiler本体、C++20を独立試験harnessに使う意味に解釈した。普及率について定量的な市場調査はしておらず、AI向けの正確性・効率が他形式より高いという結論でもない。

## 2. 採用source契約 AIC/0.2

### 2.1 字句・改行規則

1. 入力はASCIIだけを許す。UTF-8 BOM、NUL、非ASCII文字、裸のCRは拒否する。物理行末はLFまたはCRLF。最終行の終端改行は任意。
2. 字句上の水平空白はASCII spaceとtabだけ。行頭・行末・区切り記号の周りの水平空白を許す。各宣言、命令、block label、terminatorは物理1行に置き、行継続は認めない。
3. セミコロンから物理行末までをcommentとする。comment行と空行は構文要素間で無視する。引用文字列・escape sequenceはない。
4. keywordとoperation名は大文字小文字を区別する。operation tokenはidentifierをdotで1回以上つないだ形（例 add.wrap.u64）、version tokenは数字列・dot・数字列で構成する。dotはこれらのtoken内に含む。句読記号 = : ( ) [ ] , -> は個別token。value referenceは % とidentifier、block referenceは ^ とidentifierを連結したtokenで、間に空白を挟めない。数値tokenとidentifierの連結は認めない。word tokenどうしは最低1個のspaceまたはtabで分離し、句読記号の隣では空白を省略できる。
5. identifierはASCII [a-z][a-z0-9_]{0,62}。先頭小文字英字と、小文字英字・数字・underscore 0〜62文字で構成する。value IDとblock IDはmodule内でそれぞれ一意。
6. u64整数は符号なし10進または0x付き16進。10進は0か、1〜9で始まる最大20桁。16進prefixは小文字0x、数字は1〜16桁でA〜Fの大文字・小文字を許す。値は0..18446744073709551615。符号、桁区切り、指数、桁あふれは拒否する。
7. 数値解析は検査付き変換を使い、host言語のinteger overflowで意味を変えない。範囲外は診断を返す。

### 2.2 文法

以下はcomment・空行を除いた構文レコード列の文法である。headerは単独行、function_headerは開始波括弧までの単独行、block_headerはラベルとcolonの単独行、instruction/terminatorはそれぞれ単独行、function_endは閉じ波括弧だけの単独行とする。句読記号の周りには任意の水平空白を置ける。word tokenどうしは前節に従う。+は1回以上、*は0回以上、|は選択を示す。EBNFの角括弧はメタ記号で、Phiの実際の角括弧とは区別する。

~~~ebnf
module          = header, function ;
header          = "AIC", version ;
version         = digit, { digit }, ".", digit, { digit } ;

function        = function_header, block+, function_end ;
function_header = "fn", "aic_main", "(", parameter, ")",
                  "->", "u64", "{" ;
function_end    = "}" ;
parameter       = value_def, ":", "u64" ;

block           = block_label, ":", instruction*, terminator ;
instruction     = const_u64 | add_u64 | sub_u64 | eq_u64 | phi_u64 ;
const_u64       = value_def, "=", "const.u64", integer ;
add_u64         = value_def, "=", "add.wrap.u64", value_ref, ",", value_ref ;
sub_u64         = value_def, "=", "sub.wrap.u64", value_ref, ",", value_ref ;
eq_u64          = value_def, "=", "eq.u64", value_ref, ",", value_ref ;
phi_u64         = value_def, "=", "phi.u64", phi_input+ ;
phi_input       = "[", block_ref, ",", value_ref, "]" ;

terminator      = branch | conditional_branch | return_u64 ;
branch          = "br", block_ref ;
conditional_branch
                = "br.if", bool_ref, ",", block_ref, ",", block_ref ;
return_u64      = "ret.u64", value_ref ;

value_def       = VALUE_TOKEN ;
value_ref       = VALUE_TOKEN ;
bool_ref        = VALUE_TOKEN ;
block_label     = BLOCK_TOKEN ;
block_ref       = BLOCK_TOKEN ;
VALUE_TOKEN     = "%", identifier ;
BLOCK_TOKEN     = "^", identifier ;
identifier      = lower, { lower | digit | "_" } ;
integer         = decimal | hexadecimal ;
decimal         = "0" | nonzero_digit, { digit } ;
hexadecimal     = "0x", hex_digit, { hex_digit } ;
lower           = "a" | "b" | "c" | "d" | "e" | "f" | "g" | "h" | "i"
                | "j" | "k" | "l" | "m" | "n" | "o" | "p" | "q" | "r"
                | "s" | "t" | "u" | "v" | "w" | "x" | "y" | "z" ;
digit           = "0" | nonzero_digit ;
nonzero_digit   = "1" | "2" | "3" | "4" | "5" | "6" | "7" | "8" | "9" ;
hex_digit       = digit | "a" | "b" | "c" | "d" | "e" | "f"
                        | "A" | "B" | "C" | "D" | "E" | "F" ;
~~~

EBNFは構文レコード上の順序を表す。lexical productionである value_def/value_ref/bool_ref/block_label/block_ref はそれぞれ単一tokenで、%または^とidentifierの間に空白を入れない。version tokenは数字列、dot、数字列を連結した形。u64の桁数と数値範囲は字句規則・意味検査の双方で上限を確認する。

token grammarに加え、versionは厳密に0.2だけを受理する。関数名・引数数・引数型・戻り値型も固定する。最初のblockは ^entry:、他のblock labelは一意。operand数・型・definition ID・terminator位置は文法通りでなければならない。文法に合うが未対応のversionはE_VERSION、字句・構文不正はE_SYNTAX、命令位置の未知operation名はE_UNSUPPORTED_OPとする。

診断はASCIIのcode、1-based physical line/byte-column、必要に応じた対象IDで表す。ASCII限定のためbyte-columnは文字columnと一致する。実装は先に該当したphaseの最初のerrorを返す。完全な複数error報告、全ケースのcross-phase優先順位、診断文の互換性はβ契約として未固定で、host errorのdetail文字列は受入判定に使わない。

| code | 意味 |
|---|---|
| E_LIMIT | 現実装の入力/object観測byte・assembler stream capture・AST規模・公開IR識別子長の容量超過（§2.5） |
| E_ENCODING | BOM、非ASCII、NUL、裸CRまたは禁止control byte |
| E_VERSION | AIC version tokenが0.2以外 |
| E_SYNTAX | token列、record位置、grammar、delimiterが不正 |
| E_UNSUPPORTED_OP | operation tokenは識別できたが本版が未対応 |
| E_DUPLICATE_ID | value IDまたはblock IDの再定義 |
| E_UNDEFINED_VALUE | value referenceの定義が存在しない |
| E_UNDEFINED_BLOCK | branchまたはPhi incomingのblockが存在しない |
| E_TYPE | operand、branch condition、return、phiの型違い |
| E_DOMINANCE | 通常useまたはphi-edge useの支配条件違反 |
| E_CFG | branch edge、terminator、entry条件が不正 |
| E_PHI | predecessorとのincoming対応が欠落・重複・余分、または配置違反 |
| E_UNREACHABLE | entryから到達不能なblock |
| E_TARGET | 未対応target/profileまたは必要feature不一致 |
| E_TOOL | assembler等の外部tool起動・実行・終了・出力読取失敗。B35のassembler runtime期限超過も含む |
| E_OUTPUT | object検査・atomic artifact保存失敗 |

上表codeは初期実装で使うcode群であり、CLI層には加えて `E_INPUT`（source読取失敗）と `E_USAGE`（CLI引数不正）がある。複数errorの報告件数・cross-phase順序・文章互換性は未採用。コンパイル失敗時に一時ファイルを成功objectとしてinstallせず、parse failureでは既存出力を維持する。

### 2.3 型・実行意味・CFG条件

- u64は64-bit unsigned bitvector、boolはtrue/falseの2値。const.u64と引数はu64、add.wrap.u64/sub.wrap.u64はu64を返し結果をmodulo 2^64で定義する。eq.u64はu64同士の値の等値を調べboolを返す。
- aic_main(x)は初期状態で引数xを持つ決定的なpure function。実行はentryから始まり、block内命令を順に評価する。brは指定blockへ移る。br.ifはtrueなら第1宛先、falseなら第2宛先へ移る。ret.u64で返ったu64が停止実行の観測結果。
- phi.u64はblock内の通常命令より前に連続して置き、blockに入るとき実際に通ったincoming edgeに対応するvalueを選ぶ。複数Phiがあれば、各incoming operandの値を遷移元末尾の同一状態から読み、全phi destinationへ**並列代入**する。Phiの並び順で値を上書きしてはならない。Phi operandは通常命令位置でなくedge上のuse。Phiを通常命令の後に置いた場合は拒否する。
- 関数parameterはentry blockで定義されたSSA valueとして扱い、全到達blockで利用可能。SSA valueは一度だけ定義する。通常useでは定義がuseを支配し、同一blockなら定義命令はuseより前に置く。Phi incoming useは当該predecessor末尾で値が利用可能であること。add/sub/eqはu64を2個受け取り、branch conditionはbool、returnとphi incomingはu64。型不一致、未定義use、支配関係違反を拒否する。entryに前駆edgeはないためPhiを置けない。
- blockは一つのterminatorで終わり、その後に命令を書けない。branch先は存在する。br.ifのtrue/false宛先が同一なら重複edgeとして拒否する。CFG上、同じpredecessor/successor間のedgeは高々一つ。
- 各Phiはblockの全predecessor blockについて正確に1個のincomingを持つ。重複label、欠落label、余分なlabelを拒否。incomingの記載順は実行意味を持たない。
- ^entryは他blockからedgeを受けない。entryから到達できないblockはE_UNREACHABLEで拒否し、黙って削除しない。loop/backedgeは許す。
- 非停止loopは有効で、return結果を持たない実行と定義する。interpreterがfuel限界に達した場合は非停止の証明ではなくINCONCLUSIVE。fuel切れでcompile成功・意味一致を主張しない。
- 採用済み初期範囲にmemory、pointer、I/O、syscall、global、複数function、function call、exception、atomic/thread、float/vector、undefined/poison、nondeterminism、外部副作用はない。外部観測は停止時の返却値のみ。

**重複edge・unreachable blockの反例方針：** br.if %b, ^join, ^joinは同一predecessorから同一successorへ異なる2 incoming値を与える曖昧なPhiを作るため拒否する。entryから到達不能なblockを含むmoduleも、dead codeの意味・診断・削除時点が未定義になるので拒否する。どちらも最適化で修復して成功させない。

### 2.4 入力依存性の限界と採用済み最小範囲

引数なしu64返却の停止関数は、実行環境との入出力も状態もないため、外部から観測できる値はprogramごとに固定された定数でしかない。branchやloopがあっても、停止する場合の返却値は一つに決まる。前版のmain-only案は経路確認には使えても入力依存計算の有用性を示さない。

Owner採用済みの最小範囲は1個のu64 argumentを取り、少なくともx+1 (mod 2^64)、比較による分岐、loop state更新を表せるpure functionとする。入力ごとに異なる結果を返せるが、memory、複数値の状態、call、I/Oがなく、実用的な任意applicationを表現できる保証はない。実用βと呼ぶか、追加機能が必要かはOwner判断であり、ここではmemoryを先取り追加しない。

### 2.5 現実装の容量制限（B33〜B35）

AGENTSの`BUDGET`規律に沿い、新たな実装上限を置く。これはOwner採用済み演算意味・文法の変更やβ資源契約の確定ではない。容量を超えた有効sourceも本実装では処理を拒否するため、実装の受理容量は従来より狭まる。

| 資源 | 上限（inclusive） | 検査入口・数え方 |
|---|---:|---|
| source bytes | 1,048,576（1 MiB） | comment・空白・改行も含む。CLIは最大1,048,577 byteを読み、`parse`はencoding/lex前に同一定数で検査 |
| assembler objectの観測bytes | 8,388,608（8 MiB） | B34。regular-file判定後、driverは最大8,388,609 byteを読み、ELF bytes入口はheader解析前に同一定数で超過を拒否。未参照paddingも含む |
| GNU as stdout / stderr capture | 各65,536 byte（64 KiB） | B35。`as --version` queryとassembly invocationごと、streamごとに上限。超過は上限+1 byteの観測で`E_LIMIT` |
| GNU as invocation runtime | 30秒 | B35。version query・assembly processのspawn後、direct childが実行を続けている場合に期限を検出。期限超過は`E_TOOL` |
| blocks | 256 | `validate`冒頭。entryを含み、定義表・CFG・支配集合の構築前に拒否 |
| instructions | 16,384 | 全blockのinstruction総数。Phiを含み、parameterとterminatorは含めない |
| Phi incoming records | 65,536 | 全Phiのincoming総数。重複や意味不正も計数し、要素の名前を走査する前に総数を検査 |
| 公開IRの識別子bytes | 各63 | parameter、block/value定義、全operand、branch先、Phiのblock/value参照。cloneや名前入り診断の前に長さを検査。source字句の既存63-byte制限も同一定数を使用 |

数値正本は`src/limits.rs`。1 MiBは前処理の入力増幅を有限化する実装予算、256 blockは現行BTreeSet支配集合の最大65,536要素を抑える予算であり、実測から求めた性能閾値ではない。命令とPhi incomingも別個に有限化する。各定数は将来の実装・証拠に応じ変更可能で、長期互換性や最大規模programのnative実行可能性は保証しない。

超過は`E_LIMIT`であり、AIC意味上の不正とは区別する。source byte検査はencodingより先、AST検査はblock数→命令総数→Phi incoming総数→識別子長→既存意味検査の順。CLIの同一input/output拒否は読取前の`E_OUTPUT`を維持する。`parse`単独はbyte上限だけを検査し、AST容量検査は`validate`、`evaluate`/`evaluate_many`、公開emitter、driverの検証経路で作用する。

B34の8 MiBはobjectの観測量を有限化する新規実装予算で、ELF規格の最大file sizeでも、最大sourceから得るobject sizeの証明でもない。8 MiB超でも一般ELFとして有効なfileを容量拒否し得る。`E_LIMIT`は既存outputを保持してinstall前に返し、通常のprivate staging cleanupを行う。文字列表は非empty表の先頭/末尾NULを検査済みなので、範囲内indexには後続NULが存在する。section名はindexだけ、必須symbol名は`aic_main\0`の固定9 byteだけを照合し、長い文字列の反復NUL走査を除去する。suffix/byte名・空表index0例外を維持する。

B35のassembler budgetは各streamのcapture量とdirect childの通常実行を限定する実装予算であり、process tree全体の制御ではない。同期nonblocking socket pairで両streamを反復drainし、reader threadを作らない。上限超過または期限到達時はdirect childへkillを要求し、waitで回収する。子孫processはkill・waitしない。direct child終了後はその時点で読み取れるbyteだけをfinal drainし、子孫が後から出すbyteは追跡しない。期限後のOS process reap待ちにも独立したwall-time上限はない。これらはcompiler全体のRSS・全allocation・CPU/wall time・stack利用量・一時disk全量・file open/read待ちの上限ではない。parserはbyte上限内でtoken/Recordを先に蓄積し、直接AST構築の呼出側allocationは制限しない。生成disk量、検査後の敵対的file変更も未保証。β契約は§8のOwner判断に残す。

## 3. AI操作形式の未採用比較候補

AIC/0.2は初期実装用に採用したSSA/CFG textであるが、AI操作に最適とは言えない。次のAIC-J/0.1は未採用の構造化JSON比較仮説であり、textとJSONの二択が参照候補全体を尽くすわけではない。ほかの言語・IR・DSL・schema・文法・形式表現の枝は[参照地図](../research/02_既存言語・表現参照地図.md)に開いておく。現状の契約選択は初期実装を進める範囲の指定で、全候補の比較やAI効率実験の結論ではない。資源制約による比較の保留は排除・不採用と区別して記録する。

~~~json
{
  "format": "AIC-J/0.1",
  "function": {
    "name": "aic_main",
    "params": [{"id": "x", "type": "u64"}],
    "result": "u64",
    "blocks": [
      {
        "id": "entry",
        "ops": [
          {"id": "one", "op": "const.u64", "value": "1"},
          {"id": "y", "op": "add.wrap.u64", "args": ["x", "one"]}
        ],
        "term": {"op": "ret.u64", "value": "y"}
      }
    ]
  }
}
~~~

## 4. target / ABI / object比較記録

Linux x86-64 / System V ABI / ELF64 ET_RELを初期実装targetとしてOwnerが採用した。2026-11-11にCPU floorとしてAMD64 psABI 1.0 `baseline`、gABI共通object参照版としてELF Object File Format 4.2を追加採用した。`x86_64-linux-gnu`はそのCPU floorを表すプロジェクト固有aliasである。現行命令formsとELF64 ET_RELの限定条項を一次資料と局所試験で照合したが、全条項の規格適合を意味しない。AArch64とWindows x64は未採用の比較対象である。

| 項目 | Linux x86-64 | Linux AArch64 | Windows x64 |
|---|---|---|---|
| ISA | AMD64/x86-64。現行codegen命令をIntel SDM/AMD APMで照合済み。AMD64 psABI 1.0 `baseline`を最低条件として採用。GNU asに`-march=generic64`を渡す | AArch64 base候補。mandatory feature・例外はArm ARM版を決めて選ぶ | x86-64。Linux候補と同じ命令意味を使えてもABI/object規格は別 |
| 関数ABI | System V AMD64 psABI supplement v1.0、LP64。第1u64引数RDI、返却RAX | AAPCS64 2026Q3候補。第1u64引数/返却X0 | Microsoft x64 ABI。第1u64引数RCX、返却RAX。callerは4 register引数分32-byte shadow storeを提供 |
| object | ELF64、EM_X86_64、ET_REL | ELFCLASS64、EM_AARCH64 (183)、ET_REL | AMD64 COFF object (.obj, machine 0x8664)。link後はPE32+ image (optional-header magic 0x20b)。COFF objectとPE imageを同一物と扱わない |
| 外部境界 | Linux userspace function object。syscall/APIなし。通常ABI呼出しharnessが実行 | 同左。Arm64 Linux harnessまたはemulator | Win64 harness。初期functionはsyscall/Win32 APIなし。EXE生成・loader・runtimeは別 |

^zero_case:
  %zero_result = const.u64 0
  br ^join
^other_case:
  %incremented = add.wrap.u64 %x, %one
  br ^join
^join:
  %result = phi.u64 [^zero_case, %zero_result] [^other_case, %incremented]
  ret.u64 %result
}
~~~

この設計fixtureはx=0なら0、それ以外ならx+1 mod 2^64を返す。実装の`examples/branch_phi.aic`は同じ基本機能にwrap-subtractを加え、全0..65535と境界入力を検査する。実装済みの`examples/loop_swap.aic`は^headのPhi pairをa<-b, b<-aで更新し、input回数だけ反転してreturnする。これらは有限のQC fixtureであり、すべてのprogram/inputやISA/ABI規格適合の証明ではない。受入閾値、input bank完全性、対象CPU母集団、必要な形式証明範囲はOwner判断である。

loop/Phi-cycle fixture:

~~~text
AIC 0.2
fn aic_main(%n: u64) -> u64 {
^entry:
  %zero = const.u64 0
  %one = const.u64 1
  br ^head
^head:
  %i = phi.u64 [^entry, %zero] [^step, %next_i]
  %a = phi.u64 [^entry, %zero] [^step, %b]
  %b = phi.u64 [^entry, %one] [^step, %a]
  %done = eq.u64 %i, %n
  br.if %done, ^exit, ^step
^step:
  %next_i = add.wrap.u64 %i, %one
  br ^head
^exit:
  ret.u64 %a
}
~~~

n=0,1,2,7での期待値は0,1,0,1。headのbackedgeではa<-bとb<-aが同時に行われるため、逐次slot/register copyでは値を壊す可能性がある。実装はこのcycleをscratch領域でstageしてからcommitし、0..255をobject/interpreterで照合する。検証用の負例は (a) br.if %c, ^join, ^joinによる重複edge、(b) ^entryから到達不能な ^ghost block、(c) predecessor不足または重複を持つphi incoming、(d) 支配しないblockで定義した通常use。負例はunit testsに実装済みである。

## 8. 未決定の品質・規格項目

1. GNU asの実行path/versionをbuild environmentに固定または検査する。現在はPATH上の`as`を起動し、GNU binutils 2.44のみ観測した。
2. frame/scratch/resource上限、diagnostic cross-phase precedence・compatibilityをβ契約として定める。現compilerはsigned disp32を超えるframeと§2.5の実装容量超過を拒否するが、これをβ保証へ昇格しない。
3. QC/QAの受入母集団・閾値、AI向け形式比較実験の有無、形式的意味保存証明の必要範囲を決める。
4. 将来memory/I/O/call等を含めるか、実用βに必要な機能、β公開可否・時期を決める。

### 8.1 Owner採用記録と適用境界
