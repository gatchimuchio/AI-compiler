## 1. 施工原則

`全体の意味・責任境界の設計 → 一気通貫の変換実装 → 実物QC → 対象別QA → Owner最終公開判断`を基本とする。

小さな確認単位を積み上げること自体を成果としない。宣言した対象範囲について、AI文字列から規格適合の生成物まで、接続済みの仕事を成立させる。

全命令・全CPUの網羅率100%は初期β版の条件ではない。一方、対応を宣言した範囲の適合性は緩和しない。

## 3. 1週間ローンチ構想の位置づけ

「Codexを活用し、約1週間で限定対象のβ版を目指す」は**開発仮説**であり、確約済み納期ではない。R1・R2で実装範囲を確定してから工程日数を再評価する。

各日ごとの形式的な完了を要求する代わりに、意味のある機能の接続と、対応範囲内の成立証拠を工程終了条件にする。

## 4. 進捗・証拠分類

- `NOT_STARTED`：未着手
- `DESIGNED`：要求・仕様が定義された段階。実装済みではない
- `CODE_PRESENT`：コードは存在するが必要な実接続は未確認
- `WIRED`：入口から生成物まで実接続された段階。品質合格とは別
- `QC_OBSERVED`：対象実物の試験・解析結果が記録された段階
- `QA_SCOPED`：対象・条件を限定して必要な適合性が立証された段階
- `BLOCKED`：不整合・権限・証拠等により工程が進められない
- `OUT_OF_SCOPE`：現行受入対象外

未確認を`PASS`や`RELEASED`へ昇格させない。完了証拠はcommit、試験・監査記録、対応ターゲット、必要なリビジョン情報と対応づける。

## 5. 完了権限

Codexは調査、設計案、実装、検証、差分監査、通常のGit保存を担当できる。初期ターゲット・仕様の主要変更、品質要求の緩和、β公開、商用化はOwner判断事項とする。

## 6. 直近バッチと依存条件（2026-11-09）

- **B1／R1：** docs/research/01_既存技術・規格調査.mdに既存compiler、Linux ABI/ELF、Windows x64 ABI/COFF-PEの固定版資料を記録。公式ISA配布先とELF gABIはCONNECT 403、GitHub search APIも403で、同一原典の適正な代替配布を特定できなかった。ISA命令仕様とELF共通規則は未観測のまま残り、R1進行中。
- **B2／R2設計候補：** docs/proposals/01_初期変換契約案.mdを改訂。AIC/0.1監査、入力依存function候補、字句・構文・意味、Phi並列代入、AI向け形式比較、Linux/Windows target比較、変換経路、実装案と受入fixtureを記録。**すべて未採用候補**であり、Owner判断前の実装対象ではない。
- **Owner採用ゲート：** 初期対象（ISA/ABI/OS/形式）、入力構文・意味、コンパイラ実装技術、生成物作成経路、初期受入範囲が現行仕様に採用されるまでR3の設計依存実装を開始しない。
- **B3／R3以降：** 採用後は全体の変換経路を先に接続し、実物QC→対象別QA→Owner公開判断へ進む。空の雛形や資料の量でB1/B2/B3を完了とみなさない。

R1/R2は調査・提案段階であり、R0完了・文書整備をコンパイラ実装の進捗へ加算しない。
