## 対象とrun 01との関係

run 01ではAIC 0/60、JSON 0/59のstrict format parseとなり、全完了回答に空の`<think>...</think>` wrapperが含まれた。run 01のraw data・採点結果はそのまま保持し、wrapを除去して再採点していない。

`llama-cpp-python==0.3.16`の現物を確認すると、`Jinja2ChatFormatter.__call__`は任意keywordを受け取る一方、内部Jinja renderへ`enable_thinking`を渡さず、chat-completion handlerもそのkeywordをformatterへforwardしない。run 01の`/no_think`はsystem messageの文字列であり、Qwen3のtemplate変数を設定していなかった。run 01で観測したwrapperは、この生成設定の不足と整合する。

本追試では、同一のGGUF組込みtemplateに`enable_thinking=false`を明示してAIC/JSONの両方へ適用した。課題、schema card、system/user bytes、モデル、sampling、出力上限、seed方式、validator、oracle、compiler/consumerは変更していない。template設定の違いを評価後にrun 01へ混ぜず、別sampleとして事前登録した。

事前登録前の非課題診断は1回だけで、`Reply with the exact text OK and nothing else.`に対し`OK`を返し、生成本文にthink wrapperはなかった（[診断scriptと全記録](../../experiments/g3-edit-pilot-2026-11-13/diagnostics/)）。これはE1–E6に含めず、採点母数にも加えていない。

追試runnerの呼出し前setupは2回停止した。1回目はprompt hashのmanifest階層参照誤りでモデル読込前に終了。2回目はmanifestに`runner_version`がなく、model/prompt preflightの完了後、最初のtask call前に終了した。両方とも課題呼出し0件で、エラーとready preflightを保存した。入力・課題・採点基準を変えず、版とhashを更新してから初回課題callを行った（[`setup_attempts.jsonl`](../../experiments/g3-edit-pilot-2026-11-13/run02/setup_attempts.jsonl)）。

## 観測結果

| 段階 | AIC/0.2 | AIC-J/0.1 | 適用範囲 |
|---|---:|---:|---|
| strict parse | 50/60 | 50/60 | 失敗はAIC E6が10件、JSON E5が10件。各taskで集中 |
| common validator | 50/60 | 50/60 | parse受理分は全て通過 |
| production compiler + C++ consumer | 50/60 | 50/60 | validator受理分を隔離object化して実行 |
| compiled output = candidate operation oracle | 50/50 | 50/50 | 実行objectを候補programの独立oracleへ照合 |
| exact requested edit | 20/60 | 19/60 | 要求外node/field変更も不合格 |
| strict pilot success | 20/60 | 19/60 | exact editと22固定入力のtask oracle一致を両方要求 |

task別strict pilot success：E1 AIC 0/10・JSON 0/10、E2 10/10・10/10、E3 0/10・0/10、E4 0/10・9/10、E5 10/10・0/10、E6 0/10・0/10。paired差はE4でJSON側+9、E5でAIC側+10、その他0。全体差はAIC側+1件にとどまり、6 synthetic task内でも課題依存の反対方向差が相殺している。

100件のstrict parse/validator受理分はすべてproduction compiler、C++ consumer、22入力のcandidate oracleを通過した。固定入力に対するtask oracle出力一致はAIC 30/60、JSON 20/60だった。exact editを通さないが有限入力では期待値と一致した出力もあるため、pilot successはプロトコルどおりrequested editも必須とした。

JSON E5の10件はJSON syntax error（property名のquote不足）でparse不合格。AIC E6の10件は`E_SYNTAX: expected value operand`。120生成本文のいずれにも空think wrapperは含まれなかった。候補profileやproduction codeは変更せず、AIC-J/0.1は未採用のまま。

## 判定と限界

この追試はtemplate欠落で止まったrun 01の生成設定を補正し、事前固定した局所task bankで比較可能な出力を得た。strict parseとconsumer経路は成立したが、6件・10 pair/task・単一4B modelの探索標本であり、一般的な編集性能、AIC形式の優位性、最適性、G3全体、QA、採用を確定しない。対照と候補の全体pilot-success差+1から勝者は選ばない。run 01とrun 02は別条件・別sampleであり、poolしない。

production sourceは未変更。run 02のstrict scorerはrun 01と同じ`score_pilot.py`を用いた。schedule、pair seed/order、全prompt/response UTF-8 bytes、frozen input/model/template/compiler hashes、raw/scored hash、object-oracle整合を[`audit.json`](../../experiments/g3-edit-pilot-2026-11-13/run02/audit.json)で照合し全25 check PASS。

model weightsは既存の`/tmp/aic-g3-pilot-2026-11-13/`から再利用。run 02のhelper build、normalized source、object、consumerは別の`/tmp/aic-g3-pilot-run02-2026-11-13/`に保管し、model weight/object/buildはGitへ含めない。raw prompt/responseと採点は`experiments/g3-edit-pilot-2026-11-13/run02/`へ記録。
