## N1570が決める規則と残す選択

| 条項 | このsourceに関係する規則 | 残る選択 |
|---|---|---|
| §6.2.5p15、§6.3.1.1p3 | plain `char`は` signed char`か`unsigned char`のどちらかと同じrange/representation/behaviorを持ち、符号の扱いはimplementation-defined | `char c, e`の符号特性 |
| §6.3.1.3p3 | 符号付きdestinationが値を表せないinteger conversionは、結果がimplementation-definedか、implementation-defined signalが発生する | `128`を8-bit signed `char`へ格納する結果、またはsignal |
| §6.5.7p5 | 負のsigned integerのright shift結果はimplementation-defined | `h`が負になった後の`h >> 16` |
| §6.5.16p3 | assignment expressionは代入後のleft operand valueを持つ | `h = c = d % g`では、`c`への変換後の値が`h`へ渡る |
| §6.7.9p10 | 初期化されないstatic storage durationのarithmetic objectはzero-initialized | 外部定義`int a`は初期値0 |

N1570だけで全入力/全target向けの期待出力は定まらない。少なくともplain `char`の選択、値域外conversion、負値right shiftに実装選択が残る。signed conversionでは実装定義結果に加えてsignalの選択肢もある。

## 条件を固定した手計算

以下は一般規則ではなく、`CHAR_BIT=8`、`short` 16-bit、`int` 32-bit、8-bit signed `char`が-128を表現できるtargetでの条件付きtraceである。`main`は`f(129, 128)`を呼び、global `a`はzero-initializedなのでloop bodyは`a=0`と`a=1`で実行される。

1. 1回目は`h=128`。`short`の値はこのtargetで`int`へinteger promotionされ、非負の`128 >> 16`は`128 / 2^16`の整数部、つまり0。`b`を出力するので最初のlineは`0`。その後`d=128`、`d % g = 128 % 129 = 128`。
2. `c = 128`の結果はplain `char`のchoiceに依存する。plain `char`がunsigned 8-bitなら`c=128`、assignment expressionも128を返し、次の`h`は128。2回目の`h >> 16`も0となり、条件付き出力は`0\n0\n`。
3. plain `char`がsigned 8-bitで、実装が範囲外の128を`-128`へ変換すると選べば、次の`h`は-128。2回目の`h >> 16`はN1570上implementation-definedであり、arithmetic right shiftを選ぶ実装では-1となる。ただしその前に`e = b * h`を評価し、`(-1) * (-128) = 128`をplain signed `char`へ代入するため、ここにもimplementation-defined result/signalがある。実装が実行を継続する結果を選んだ場合、その次の`printf`は`-1`を出力し、条件付き出力は`0\n-1\n`となる。

これらはN1570が要求する二つの出力ではなく、実装選択で結果が変わることを示す例である。B62で`0\n-1\n`を得た事実はGCC 14.2.0-19とGCC 15.2.0の固定build/targetでの観測であり、C11必須結果ではない。

## G2上の意味と限界

- **portable C11 oracle：利用不可。** 元sourceのままC11から一意の完全stdoutを定めることはできない。
- **独立semantic oracle：NOT_RUN。** このB64は規則監査と手計算であり、独立実装した実行oracleではない。
- **compiler-specific oracle：別途定義可能。** plain `char` signedness、signed conversionの選択、negative shiftの選択、target data modelを文書化し固定する必要がある。B62のpreregistered stdoutは元reporterの再現期待を採ったもので、これらの選択を独立に固定してはいない。
- implementation-defined behaviorがあることだけで、同一compilerの最適化flag間の出力差を正当化しない。GCCの実装選択とflagの契約を固定した別の評価が必要であり、B64は原reporterのflag差の正誤を裁定しない。
- B64は単一sourceとN1570の限定照合で、他C版・他target・全GCC挙動やG2全体へ一般化しない。native execution、独立oracle、AICompiler testsは**NOT_RUN**。
