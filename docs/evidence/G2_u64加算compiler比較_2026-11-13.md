## 問いと課題

同じ意味「unsigned 64-bit入力へ1を加算し、`2^64`でwrapした値を返す」を、採用済みAIC/0.2、GCC 14.2.0のC11 frontend、rustc 1.99.1のRust frontendで、Linux x86-64 ET_REL objectまで変換した時の実objectとconsumer結果を比較する。自然言語要求とAIC/0.2は[G1単一課題観測](G1_単一課題観測_2026-11-13.md)の同じ合成例を使用する。

要求文はCodex作成の合成例で、Ownerの製品要求ではない。生成側・要求作成者は同じCodexセッションである。GCC/Rust compilerのbackend選択を特定のoptimization passへ帰属させず、出力だけを観測事実として記録する。

## 意味と入力

| 系 | 入力ソース |
|---|---|
| AIC/0.2 | G1記録にある`const.u64 1`、`add.wrap.u64 %x, %one`、`ret.u64 %result` |
| C11 | `uint64_t aic_main(uint64_t x) { return x + UINT64_C(1); }` |
| Rust 2024 | `#![no_std]`、`#[unsafe(no_mangle)] pub extern "C" fn aic_main(x: u64) -> u64 { x.wrapping_add(1) }` |

C sourceでは`uint64_t`が利用可能なexact-width unsigned typeであることをこのtargetの実際のheader/typeで使う。WG14 N1570 §6.2.5p9はunsigned arithmeticのmodulo規則を記述し、§7.20.1.1はexact-width integer typedefを定義する。この文書は2011-04-12付の公開Committee Draftで、ISO発行版そのものとは表示しない。Rust 1.99.1の`u64::wrapping_add`文書はmodular additionとして型境界でwrapする、と説明する。一次資料と取得時hashは下記に記録した。

## 条件と実測

| 経路 | Compiler/flags | 実objectの`aic_main` | Object size/hash |
|---|---|---|---|
| AIC/0.2 | project compiler at base HEAD、GNU as 2.44 `--64 -march=generic64`。このbackendはstack slotsを使い、最適化設定なし | `.text` 46 bytes。G1記録のdisassemblyを参照 | 744 bytes / `fd6a266fb5b88242e2f49e21bc3725d063f889b5e62521a74cb0b0addbeeee0a` |
| C11 | GCC (Debian 14.2.0-19) 14.2.0。`-std=c11 -O2 -march=x86-64 -mtune=generic -fno-pic -fno-pie -fno-stack-protector` | `.text` 5 bytes: `lea 0x1(%rdi),%rax; ret` (`48 8d 47 01 c3`) | 1080 bytes / `5dfca56af7b48446f2be1cbb18790579e427e842f4a259ff56928829e4695152` |
| Rust 2024 | rustc 1.99.1 / LLVM 23.1.1。`--target x86_64-unknown-linux-gnu -C opt-level=2 -C target-cpu=x86-64 -C relocation-model=static -C panic=abort` | `.text.aic_main` 5 bytes: `lea 0x1(%rdi),%rax; ret` (`48 8d 47 01 c3`) | 976 bytes / `2eeaebf1d2674c874bba414a7e3f5cea25b4dd00bd832d62b419c85d22bd982c` |

3 objectはすべてELF64 little-endian x86-64 `ET_REL`。各objectを個別に、同じGNU g++ 14.2.0 / C++20 consumer (`tests/harness.cpp` + `tests/abi_probe.S`)へlinkし、入力`0, 41, 18446744073709551615`で実行した。結果は各経路とも`1, 42, 0`。別計算`(x + 1) & (2^64 - 1)`も`1, 42, 0`で一致し、harnessは正常終了した。

function byte数はこの一課題での観測である。GCC/Rustは`-O2`相当で、project AIC backendには同等の最適化passがない。全object sizeは`.comment`、`.eh_frame`等のmetadataが異なるため直接の効率比較に使用しない。実行時間、throughput、資源、他入力への一般化を計測していない。

### 再実行

リポジトリrootで実行。AIC/0.2 sourceはG1記録と同じ合成課題である。

```sh
set -eu
WORK=/tmp/aic-g2-compare-20261113
mkdir -p "$WORK"
rm -f "$WORK/aic.o" "$WORK/gcc.o" "$WORK/rust.o" \
  "$WORK/consumer-aic" "$WORK/consumer-gcc" "$WORK/consumer-rust" \
  "$WORK/aic.actual" "$WORK/gcc.actual" "$WORK/rust.actual"
cat > "$WORK/ai-output.aic" <<'EOF'
AIC 0.2
fn aic_main(%x: u64) -> u64 {
^entry:
  %one = const.u64 1
  %result = add.wrap.u64 %x, %one
  ret.u64 %result
}
EOF
cat > "$WORK/gcc.c" <<'EOF'
#include <stdint.h>
uint64_t aic_main(uint64_t x) {
    return x + UINT64_C(1);
}
EOF
cat > "$WORK/rust.rs" <<'EOF'
#![no_std]

#[unsafe(no_mangle)]
pub extern "C" fn aic_main(x: u64) -> u64 {
    x.wrapping_add(1)
}
EOF
printf '0\n41\n18446744073709551615\n' > "$WORK/inputs.txt"
PATH=/home/agent/.cargo/bin:$PATH cargo run --locked -- compile \
  --target x86_64-linux-gnu "$WORK/ai-output.aic" -o "$WORK/aic.o"
gcc -std=c11 -O2 -march=x86-64 -mtune=generic -fno-pic -fno-pie \
  -fno-stack-protector -c "$WORK/gcc.c" -o "$WORK/gcc.o"
PATH=/home/agent/.cargo/bin:$PATH rustc --edition=2024 \
  --target x86_64-unknown-linux-gnu --crate-type=lib --crate-name=g2_rust \
  --emit=obj -C opt-level=2 -C target-cpu=x86-64 \
  -C relocation-model=static -C panic=abort "$WORK/rust.rs" -o "$WORK/rust.o"
g++ -std=c++20 -O2 -mno-red-zone -Wall -Wextra -Werror \
  tests/harness.cpp tests/abi_probe.S "$WORK/aic.o" -o "$WORK/consumer-aic"
g++ -std=c++20 -O2 -mno-red-zone -Wall -Wextra -Werror \
  tests/harness.cpp tests/abi_probe.S "$WORK/gcc.o" -o "$WORK/consumer-gcc"
g++ -std=c++20 -O2 -mno-red-zone -Wall -Wextra -Werror \
  tests/harness.cpp tests/abi_probe.S "$WORK/rust.o" -o "$WORK/consumer-rust"
timeout --kill-after=1s 30s "$WORK/consumer-aic" < "$WORK/inputs.txt" > "$WORK/aic.actual"
timeout --kill-after=1s 30s "$WORK/consumer-gcc" < "$WORK/inputs.txt" > "$WORK/gcc.actual"
timeout --kill-after=1s 30s "$WORK/consumer-rust" < "$WORK/inputs.txt" > "$WORK/rust.actual"
python3 - <<'PY'
from pathlib import Path

work = Path('/tmp/aic-g2-compare-20261113')
inputs = [int(line) for line in (work / 'inputs.txt').read_text().splitlines()]
expected = [(value + 1) & ((1 << 64) - 1) for value in inputs]
for name in ('aic', 'gcc', 'rust'):
    actual = [int(line) for line in (work / f'{name}.actual').read_text().splitlines()]
    assert actual == expected, (name, actual, expected)
    print(name, actual)
PY
```

## 適用限界

- 一つのCodex作成合成課題、3つの入力値、1つのhost環境に限る。Owner由来要求の変換証拠ではない。
- GCC C11とRust 2024はsource semanticsが異なる。ここで対応させたのは当該関数の明示的なunsigned/modular-add意味だけである。
- Clangは環境に未導入。GCC/Rustの2処理系比較だけで既存compiler母集団を代表しない。
- GCC/Rustは`-O2`相当、AIC/0.2は最適化なしであり、byte差を同等最適化条件の優劣として解釈しない。
- 長期の利用実績、互換性事故、bug/repair history、別version、target別品質、性能測定、全suiteは未調査/未実施。G2は未成立のまま。
