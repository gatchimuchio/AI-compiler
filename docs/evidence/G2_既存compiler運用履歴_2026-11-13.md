## 問いと証拠の種類

G2が要求する「既存compilerの蓄積された現実の運用成果」について、GCC 14 release seriesの保守履歴、GCC trunkの誤コード報告と上流修正記録、Rust 1.98 seriesのstable-to-stable誤コード報告とpatch release記録、LLVM X86 backendのtailcc stack-argument報告とmain修正を一次資料から確認した。前記のu64 wrap-add比較（GCC 14.2.0 / rustc 1.99.1）とは対象版・処理・機能・targetが異なるため、履歴証拠として別管理する。

GCC/Rust/LLVMのrelease announcement、issue/PR状態、source-control commit/test、CI記録はそれぞれproject側またはreporterの記録である。報告された症状・version差は当該reporterの提出として扱い、このprojectでは再現していない。sourceの存在や修正記録を、母集団全体の品質・発生率・再発防止保証へ拡張しない。

## 具体例A — GCC trunk PR 116488

- GCC bug mailing-list archiveの2024-08-26報告は、GCC 15.0.0 experimental trunk、target `x86_64-pc-linux-gnu`、最適化時の`-fno-forward-propagate`条件でwrong-codeを報告した。reporterの簡約C例では、flagなしの`-O3`が`0, -1`、`-fno-forward-propagate -O3`が`0, 0`を出力したと記録する。
- 同報告は、このcaseをGCC 14.2およびそれ以前では再現しないと記載。報告時状態は`UNCONFIRMED`だった。これはstable GCC 14.2の障害報告ではなく、次世代trunkでreporterが観測した例である。
- 取得したBugzilla recordは`RESOLVED FIXED`、target milestone `15.0`、最終更新2024-11-19を表示する。recordはJeff Lawの2024-10-21 commit `r15-4532-g36e91df7716d34aa5694533837551593ec28f22b`を`PR rtl-optimization/116488`の`Fix SIGN_EXTEND source handling in ext-dce`として参照する。GCC source mirrorの固定commitは`gcc/ext-dce.cc`変更と`gcc.dg/torture/pr116488.c`を含み、同じcommit messageはPR 116488のほか116579/116915/117226も列挙する。

この資料から確認できるのは、限定されたtrunk wrong-code報告、ticket上の解決状態、15.0 target milestone、上流変更・regression testcase記録である。このprojectが報告を独立再現したわけではなく、14系へのbackportや全target QAも主張しない。

### GCC例の修正・testcase追跡

- GCC commit `r15-4532-g36e91df7716d34aa5694533837551593ec28f22b`のsource mirror patchでは、`carry_backpropagate`が`SIGN_EXTEND`のsourceを処理してsign bitをliveとして伝播し、`ZERO_EXTEND`にもoperand recursionを追加する。また`ext_dce_process_uses`でbackpropagationを最適化段階の前に移す。commit messageは、このPRを含む4件（116488/116579/116915/117226）を関連付ける。
- 同commitは`gcc/testsuite/gcc.dg/torture/pr116488.c`を新設する。testはrun directiveと`-fno-forward-propagate`を指定し、`f(129, 128)`実行後に`b == -1`を確認する。このtestは当初`char c, e`を宣言したが、後続commit `8df549fc2c0297970cb3bcadba7929088af96522`はunsigned `char`を既定とするpowerpc64le等でPR116488/117226 testがfailすると報告し、`c, e`を`signed char`へ変更した。これは回帰testの符号性portable化であり、後続のcompiler wrong-code報告ではない。
- 後続commitの説明は修正後testをpowerpc64le-linuxとx86_64-linux（`-m32/-m64`）で試し、x86_64では`-funsigned-char`の前後でも試したと報告する。修正commit `36e91df...`自身もx86_64、ppc64le、riscv64、s390x、mips64、loongarch、aarch64、m68k、alpha、hppa、sh4、sh4eb等でbootstrap/regression testをしたと記す。いずれもmaintainerによる記録であり、本projectが実行を再現した結果ではない。
- 修正commit messageには任意に複雑なRTL operandのrecursive handlingが将来再検討になる可能性も記される。今回の一次資料追跡は当時の修正とtest履歴を示し、全caseの修正完了・全target QA・後年の再発有無は示さない。GCC/Rust compiler build、GCC testsuite、Rama reproduction、本repo testsは今回NOT_RUN。

## 具体例B — Rust 1.98 vtable miscompilation

- Rust compiler issue `#161441`は2026-08-21に報告された。issueのreporterは`aarch64-apple-darwin`で、同じdownstream sourceがRust 1.97.1では動作、1.98.0ではcompiler-generated trait-object vtableのmethod entryがzeroになり、address zeroへのindirect dispatchでcrash、`nightly-2026-07-16`では再び動作したと記録した。issueにはstable-to-stable regression、miscompile、criticalのlabelが付いた。
- Rust Release Teamの2026-09-03 `1.98.1` announcementは、vtable generationのmiscompilationを1.98.1で修正したと明記し、null function pointerがemitted codeでundefined behaviorを招くと説明する。announcementの関連issue linkは`#161441`を指す。
- issueはdownstream project由来の報告。今回の作業でRama sourceをbuild/runしたり、各rustc版を再実行したりしていない。Rust Release Teamによるpatch release告知とreporterの実測記録を結び付けた観測であり、他Rust release・target・trait object全般へは一般化しない。

### Rust例の修正経路・stable backport

- Issue #161441のcommentからbackport案内とPR [#161555](https://github.com/rust-lang/rust/pull/161555) の起票をたどれる。PR #161555の本文は#158993のstable向けbackportで#161441を修正すると明記し、merge commit `48a229ceaefd4985c50990b14116b6d856af0985` はbeta cutoff後の変更がstableに影響した経緯と、`impossible_predicates`がnext solverを既定使用する点を記す。

## LLVM X86 tailcc stack-argument alignment

- この追記のrepository基底HEADは`b644f466583f655957b62642b35b02a520b11425`。調査対象はpublic LLVM upstream recordの読取に限定する。
- LLVM issue [#105223](https://github.com/llvm/llvm-project/issues/105223)は2024-08-20にX86 main branchのwrong-codeとして作成された。最初のreproducerは`tailcc`の`musttail`呼出しへ2個の`i256`を渡し、reporterはSysV ABI用のi128引数修正commit `fa1b6e6b34eb6382c451f3a06a7c52d7ac6ada1d`以降に壊れたと記す。
- 2026-10-02の追記は通常の`tailcc` callと単一`i128`でも再現すると報告し、`x86_64-pc-linux-gnu` IRで6個の`i64`引数の後にstack上へ置かれる`i128`とpointerを使う。reporterはLLVM 22.1.8で`-O0`でもexecutableがSIGSEGVしたと記録する。これはreporterの再現記録であり、本projectは再実行していない。
- PR [#235417](https://github.com/llvm/llvm-project/pull/235417)は2026-10-25に作成され、10-27 15:07 UTCにmainへmergeされた（commit `911cced04d8b4b72ae90f5ce7685a8534592ac8c`）。修正理由は、calleeが`GetAlignedArgumentStackSize(getStackSize())`分だけstack argumentをpopする一方、callerは最大stack argument alignmentへ丸めた`getAlignedCallFrameSize()`を使うため、16-byte aligned argumentかつstack sizeが8 mod 16の時にcallerがcalleeのpop量より16 bytes多い値を期待することだった。fixはguaranteed tail-call pathでcalleeと同じstack-size計算を使う。
- commitは`llvm/test/CodeGen/X86/tailcc-stack-arg-align.ll`を追加する。`llc`とFileCheckで通常callと`musttail`、`i128`、`<4 x float>`、`i256`のcodegenを照合し、file commentはPR105223を明示する。commit本文は、fix前のreproducer executableが`-O0`/`-O2`でcrashし、fix後にexit 0となったとmaintainerが報告する。GitHub commit status endpointは`success`・29 status contextで、`clang-x86_64-linux-abi-test`と`llvm-clang-x86_64-sie-ubuntu-fast`を含む。GitHub Actionsの`Build test-suite and diff`は`skipped`であり、これらのstatusを当該新規FileCheck testの個別実行結果とは扱わない。
- LLVM 23.1.5は2026-11-03公開でmain merge後だが、固定tag `llvmorg-23.1.5`のX86 sourceに修正式は見つからず、追加regression testのtag URLはHTTP 404だった。後続調査では23.1.6が11月17日の予定で未公開、固定release/23.x commitにも修正source/testがないことを確認した（[release follow-up](G2_llvm_release_followup_2026-11-13.md)）。この時点の追跡であり、将来releaseの収録内容は未確認。issueが指すLLVM 22.1.8も未修正のreporter observationとして扱う。
- この例はX86 backendのLLVM内部`tailcc`規約に関するもの。System V ABIそのものの不具合、AIC/0.2の欠陥、通常C ABI callの一般不具合とは扱わず、AIC採用範囲へ変更を加えない。

## 適用限界

- GCC 14.2 / Rust 1.99.1のu64加算比較とは別のversion/operation/targetであり、その比較の正否や品質へ直接結び付けない。
- GCC例は`x86_64-pc-linux-gnu`のGCC 15 experimental trunk、Rust例は`aarch64-apple-darwin`のRust 1.98 vtable、LLVM例はX86 LinuxのLLVM main/22.1.8とLLVM内部`tailcc`。相互に同じ意味・条件での比較ではない。
- GCC/Rust release記録と選択した3 incidentに限り、compiler familyの全release、全target、全incidentを代表しない。reportされた件数を発生率や安定性の順位にしない。
- unreported failures、修正後の独立検証、backport/採用率、downstream outage費用、別versionとの再発、別CPU/OSでの品質、長期利用者母集団は未調査。G2は未成立のまま。
- 今回はpublic primary sourcesの読取/hash取得のみ。local Clangは未導入で、LLVMを構築・実行していない。repository testsも実行していない。
