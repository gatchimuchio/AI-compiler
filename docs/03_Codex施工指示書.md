## 0. 直近の施工命令（2026-11-09）

**作業対象：** `gatchimuchio/AI-compiler` の`main`。**目的：** 調査の出典と仕様の選択根拠を確保し、Ownerが初期実装条件を判断できる状態にする。**現況：** 初期文書のみ。コンパイラ本体、ビルド・実行・適合実績は未成立。

### B1：既存技術・規格の実査（R1、着手可能）

1. `LLVM Code Generator`、`GCC Machine Descriptions`、`CompCert`について、対象となる命令選択・レジスタ割付・呼出規約・オブジェクト出力・意味保存の**機能と境界**を調べる。名前を列挙しただけで調査済みにしない。必要のない機能は除外理由を示す。
2. CPU/ISA、ABI、OS呼出境界、オブジェクト形式について、最初に実装可能な**少なくとも2つの組合せ候補**を挙げ、公式仕様、対象版、利用可能な検証手段を比較する。候補と採用済みを厳密に区別する。
3. 公式規格で要求されること、参照コンパイラ固有の設計、調査からの推論、未確認事項を別々に記録する。第三者ソースのライセンス、帰属、直接流用可否を確認する。原文・公式リンク・版・取得日・対応する解釈を保持する。
4. 成果は`docs/research/01_既存技術・規格調査.md`に**実際に確認した内容**として保存する。空テンプレートや要約だけで完了判定しない。調査対象の原文を直接同梱できないときは正規の原典URL、版、条項・ファイル位置を記録し、突合可能にする。

### B2：初期設計の採用候補（R2案、B1の未解決調査と並行して候補を先行可能）

1. `docs/proposals/01_初期変換契約案.md`を作成し、AI用入力文字列の版管理、文法、意味（操作・データ・状態・依存・制御）、明示的拒否、決定性、対象プロファイルとの分離を**具体的な候補**として示す。対象に含めない操作は非対応として列挙する。
2. 同一の代表入力から生成物に至る全経路を、入力検査→意味の確定→ターゲット依存処理→命令・出力形式生成→検査の順に追跡できるようにする。各段階の責任、成立条件、根拠、主要な失敗経路を示す。既存IRの無条件流用を前提にしない。
3. 少なくとも2つの初期ターゲット候補について、互換性、実装負荷、実機/シミュレーション検証、ポータビリティ、保守を同じ尺度で比較する。コンパイラ本体の実装言語・ビルド方式、アセンブラ/リンカ利用の是非も理由付きの採用案と代替案を提示する。
4. 受入予定テストを、意味保存・規格適合・決定性・正しい拒否・誤った成功の不在に対応付ける。検査不能な性質を形式的PASSにしない。
5. Owner採用事項とCodexが調査・提案で解決可能な事項を分離し、採用依頼を`docs/proposals/01_初期変換契約案.md`末尾に整理する。**Owner採用前の候補は現行正本ではない。**

**停止境界：** B1/B2は追加の技術選定がなくても進める。B1の未解決資料が残る間もOwner指示に基づいてB2候補を先行作成できるが、B1未完了と根拠不足を明示し、ISA profileやtargetを採用済みと扱わない。採用待ちでできる調査を止めない。一方、Ownerによる主要条件の採用前に、特定CPU/OS/言語/形式を正式仕様と決めたR3実装、公開・リリース、他リポジトリへの書込みはしない。最新指示で採用済みならその根拠を記録して進む。

**B1/B2完了条件：** 出典付きの実査結果、比較可能な採用候補、実装の入力～出力の具体的契約、反証/拒否・検査設計、未決事項が揃い、差分とremote HEADを照合して報告する。完成したコードや実機適合を主張しない。

## 1. 着手時の確認

1. Ownerの最新指示と`AGENTS.md`を確認する。
2. `docs/01_統合仕様書.md`、`docs/02_工程表.md`、本書の現行版を確認する。
3. `main`のHEAD、既存ファイル、差分、既に成立している作業を確認する。
4. 今回の対象・非対象、入力・作用・出力、対象規格、対応バージョン、責任境界を固定する。
5. 未決定事項とOwnerによる採用が必要な事項を提示する。勝手に旧リポジトリの仕様を採用しない。

## 2. 参照調査の指示

- [参照一覧](REFERENCES.md)の3リポジトリは作業規律の参照に限定する。機能、HDS内部規則、既存テスト実績、製品statusを移植しない。
- 既存コンパイラについては、まず必要な命令生成・規格制約・意味保存機能を調べる。
- 根拠の優先順位は、公式規格・当該版の現行コード・検証済み動作・明記された推論とする。
- 規格上の要求と、既存コンパイラ固有の言語体系・最適化・実装都合を分ける。
- 同じ機能の再実装や無駄な資料の重複を避け、抽出した知識を新規コンパイラの設計に使う。
- ソースコードの直接流用を検討する場合は、ライセンス互換、出典、改変、依存、保守責任を事前評価する。解析と複製は同じ行為ではない。

## 3. 実装時の優先事項

1. AI専用文字列の意味を先に定義し、処理の意味が変わらない変換経路を設計する。
2. 対象CPU/OS/ABI/実行形式の条件を明示する。
3. コンパイラ内部の変換規則を構築し、機械命令生成まで一気通貫で接続する。
4. 非対応入力・不明条件は明示的に拒否する。
5. 通常の実装段階では関連する技術確認だけ行い、統合後に実物QC・対象QAを実施する。

**禁止：** 旧機械語再設計との統合、入力をC/Rust/Pythonへ変換する方式の目的化、既存LLVM IR等の無検討な正本化、モックだけの成功、未実施検査のPASS、無関係な抽象化・依存追加、試験・安全境界の削除、実機や全OSの無限定な保証。

## 4. 責任・品質・証拠

コンパイラが責任を負うのは、その対象と規格条件での入力意味・変換・生成物の適合。CPUやOSが自身の仕様を履行する責任まで引き受けない。

- 何を検証したか、何を検証していないか、どの対象版・環境で観測したかを記録する。
- 変換・出力の意味保存、規格適合、決定性、拒否動作を対応範囲内で示す。
- 実機未検証でも規格照合・解析等の証拠を保持できるが、実機動作の実証と表現しない。
- 不具合の原因が未確定なら外部実行環境の責任と決めつけず、確認した境界だけを報告する。
- 局所成立を普遍的な能力・性能・互換性に拡張しない。

## 5. 変更と完了報告

- Ownerの明示指示の範囲だけで変更し、別リポジトリへの書込み、branch/PR作成、release作業を自動開始しない。
- 意味のある実装バッチの終了時に必要な試験、diff監査、Git保全を行う。
- 変更ファイル、具体的に成立した経路、未成立箇所、検証結果/NOT_RUN、対象・版・条件、commit/remote HEAD、次作業を報告する。
- β版の最終公開判断はOwnerに残す。
